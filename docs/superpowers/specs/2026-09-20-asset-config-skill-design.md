# asset-config skill：建立与维护项目的资源配置

日期：2026-09-20
状态：已评审，待实现
目标版本：3.12.0

## 背景

新项目第一次建 `asset-config.yaml` 很难：字段多，有些必须人来定，不读文档不知道该填什么。

现状比"难"更糟 —— `skills/generate-assets/SKILL.md` 的 description 里明确写着：

```
**不适用**：
- 项目里没 asset-config.yaml → 用 image-gen 单张或先建 yaml
```

"先建 yaml"是一句甩锅，没说怎么建。而 **description 是 Claude 判断要不要用这个组件的唯一依据**
（见本仓库 CLAUDE.md 的协作注意事项）。所以现在的实际行为是：**AI 遇到没有配置的新项目，
会直接走开**。初始化这条路径根本不存在。

## 定位：这个文件不属于 generate-assets

`asset-config.yaml` 是**项目级的资源配置**，`generate-assets` 只是它的消费者之一
（本次评审中由项目作者明确：「asset-config.yaml 包括但不限于 generate-assets」）。

这直接决定了归属：初始化不该做成 generate-assets 内部的一段指引 —— 一个文件的归属不该挂在
它某个消费者名下。就像 `package.json` 里放着各种工具的配置段，文件不属于任何一个工具。

因此新增独立 skill `asset-config`，generate-assets 降级为消费者。

## 关键约束：这个插件不只被 Claude Code 加载

它可能被别的 agent host 加载（codex、其他支持 skill 机制的 AI）。所以**交互方式不能写死成
某个 host 的专有工具**。Claude Code 有 `AskUserQuestion`（结构化选项卡片），别的 host 未必有
对等物。

咨询 codex 时它的自述值得原样记下来：

> 本次会话实际提供了 `request_user_input_async`……但**这些是当前会话暴露的能力，不能推导成
> 所有 Codex 版本、模式、客户端都一样**。OpenAI 官方文档确实定义了结构化用户输入请求，
> 但将相关接口标为 experimental。

所以按最低能力约定：

> **有结构化提问能力就使用；否则用编号文本提问。两种方式都必须保留候选值、推荐理由和用户
> 自填的可能性。协议不依赖卡片外观、一次能问几题，或者同步返回答案。**

## 目标

1. 让"项目里还没有 asset-config.yaml"成为一个有明确处理路径的场景，而不是被 description 排除
2. 把必须由人决定的事真正交给人，而不是 AI 替用户填了默认值
3. 提供一个跨阶段复用的 `check`（首次初始化、人工修改、AI 修改、后续维护都用得上）

## 非目标（及不做的理由）

这一节比目标更重要 —— 下面每一条都是评审中认真考虑过又否决的，记下来免得将来重新捡起。

### 1. 不做 `answers.json` 回填协议

初版设想是「AI 读决策清单 → 问人 → 把答案写成 answers 文件 → `init --apply` 生成 yaml」。
codex 一击推翻：

> **如果答案文件由 AI 自己写，脚本无法证明答案真的来自用户。** 即使加上 `source: user`，
> 也只是 AI 的声明。这套协议适合作为协作约定和遗漏检查，不足以成为真人确认的强保证。

契约的两端都是 AI，它既当运动员又当裁判。它真正的收益在**重放初始化、接独立表单界面、
复用已收集答案** —— 这些成为真实需求时再做。跨 host 本身不足以要求它。

### 2. 不做 `--probe` 输出决策清单

边界画错了。脚本能报事实（文件存在、列名、空值统计、唯一性、引擎标记），报不了
"哪份数据代表待生成资源""哪个目录符合项目约定"。

> 如果要求 `--probe` 独自输出完整且靠谱的决策清单，就把你已经认定需要 AI 的那部分，
> 又塞回了脚本。

正确分工：**脚本提供事实 → AI 结合项目上下文提出候选 → 用户处理真正未决的问题。**

### 3. schema 暂不为多消费者分层

现在只有 generate-assets 一个消费者。现在分段等于猜第二个消费者长什么样，猜错了改起来比
不分更痛。先在文档里标清哪些字段是给 generate-assets 的，第二个消费者出现时再拆。

### 4. 不做 `init` 生骨架

骨架会和 `examples/README.md` 的字段说明重复，两处维护。先看 AI 直接写出来的一致性够不够，
不够再加。代价是各项目的 yaml 格式可能不完全一致 —— 接受。

## 设计

### 组件

| 文件 | 职责 |
|---|---|
| `skills/asset-config/SKILL.md` | 初始化引导（给 AI 执行的指令）+ 何时触发 |
| `skills/asset-config/scripts/check_config.py` | 配置校验，独立 CLI |
| `skills/generate-assets/SKILL.md` | 改 description：把"先建 yaml"指向 asset-config |

### 初始化流程（写进 SKILL.md，由 AI 执行）

```
读项目声明与实际结构
  → 提出带依据的配置草稿
  → 只问真正未决的缺口
  → 写带注释的 yaml
  → check
  → 小样迭代
```

**"带依据的草稿"是关键**。直接照着文档写 yaml，应该意味着 AI 替用户完成了项目分析和字段
映射，而不是复制一份示例再让用户自己填空。

### 决策权限三档

清单里最需要标注的是**决策权限**，而不只是"为什么需要人定"：

| 档 | 含义 |
|---|---|
| 可推断 | 有充分项目证据即可填写，**并说明来源** |
| 必须询问 | 没有现成用户决定时必须取得回答 —— **推荐值不等于答案** |
| 可暂留 | 保留未完成状态，生成草稿，之后继续迭代 |

已有的用户决定可以复用，不必重新问。用户明确说"这些你决定"也算授权。**未回答的不能被登记
成"用户选择了默认值"。**

codex 对自己遵循率的诚实自述必须写进指引，因为它说明了为什么要标权限：

> 我不会天然把清单里的每一项都理解成必须问人。如果里面同时给了候选、依据和默认值，
> 我可能判断其中一些已有足够证据，直接采用。

### 字段的决策权限（首版）

| 字段 | 权限 | 依据 |
|---|---|---|
| `adapter` | 可推断 | `game-toolkit.yaml` 的 `engine`，或 `project.godot` / `*.uproject` 的存在 |
| `output_root` | 可推断→询问确认 | 项目里的 `ArtSource/` `assets/` `art/` 等美术源目录；候选不唯一时问 |
| `categories.<n>.data_source` | 可推断→询问确认 | 扫到的 CSV/JSON；**哪份代表待生成资源**要人确认 |
| 数据源的 id 列 | 必须询问 | 脚本能报"哪些列唯一且无空值"，选哪列是人的决定 |
| `backend` | 必须询问 | 取决于用户装没装 image-gen、愿不愿意用 laozhang |
| `model` / `chain` | 必须询问 | **依赖 `backend`** —— image-gen 用 `chain` 不认 `model` |
| `aspect_ratio` | 必须询问 | 依赖用途（图标 / 立绘 / 背景），且随构图迭代 |
| `prompt_template` | 可暂留 | AI 写第一版草稿，人在小样中迭代 |
| `style.prompt_prefix` | 可暂留 | **不强制非空** —— 风格可以写在 category 里，或用 `skip_global_style` |

**依赖关系必须体现在提问顺序上**：`backend` → `model`/`chain` → `aspect_ratio` 是一条链，
不能一次把所有选择题摊开问。后端还影响比例档位（OpenAI 路径只有三档）和参考图能力
（OpenAI 路径没有多图 reference）。

### 开放题：问目标和约束，不问成品 prompt

实测生成一张图的 prompt 要改两三轮才对（本次评审期间的荒凉场景图就改了两轮）。向导问一次
只会得到一句敷衍，人最终还是回编辑器改。

但**不等于完全不问创作意图**。该问用户答得上来的目标与约束，由 AI 转成模板：

- 这批道具用于小尺寸背包图标，还是大幅展示插画？
- 角色需要俯视、侧视还是正面？
- 沿用项目现有美术或参考图，还是探索新风格？

这些会直接改变构图和模板结构。"可爱、像素、赛博朋克"这类风格关键词可以辅助，但通常不足以
决定可用的游戏资源。

取舍：**先读现有美术约定，只补问少量缺口，然后由 AI 写出引用真实数据字段的第一版模板。**
不让用户从空白开始写，也不声称第一次问答就把模板定稿了。

### 两类"未完成"要分开

- **功能性缺失**：模板引用的字段在数据源里根本不存在 → `check` 必须报错
- **创作性未定稿**：已经能出图，但风格还没满意 → 不是错误，是迭代中

把两者混成一个"TODO"，会让人要么忽略真错误，要么被没定稿的风格卡住。

### check 的检查项

`check` 是工具侧的投资重心 —— 它在首次初始化、人工修改、AI 修改、后续维护四个阶段都复用。

1. **数据源能否加载**；id 是否缺失、重复；是否会产生同名输出文件
2. **模板占位符能否在真实条目上渲染** —— 不只是 YAML 语法正确
3. **路径解析与后端配置是否相容**（如 `/Game/` 前缀配 generic adapter、`model` 配 image-gen）
4. **是否仍有明确的未完成标记**（功能性缺失报错，创作性未定稿只提示）

两条边界：

- **输入文件必须存在；新建的输出目录不应因为尚不存在就被判错**
- **校验要在生成前自动执行一遍**，避免用户跳过独立 `check` 就把占位文本送去生图

### 完成条件是小样，不是 check 通过

`check` 能确认模板渲染得出来，确认不了画面符合预期。真正的验收：

> 用真实条目出小样 → 看结果 → 改模板。首张定方向，再换一个**差异较大**的条目检查模板
> 能否泛化。

现成的 `--dry-run`（看 prompt）和 `--names`（只跑一两个）正好承接这一步，不需要新机制。

## 对 generate-assets 的改动

`SKILL.md` 的 description 里：

```
- 项目里没 asset-config.yaml → 用 image-gen 单张或先建 yaml
```

改为指向 `asset-config` skill。两个 description 因此都保持锐利：一个管"有配置了怎么批量
生图"，一个管"怎么把配置建起来、维护好"。不用靠一句含糊的描述同时承接两种入口 —— 含糊的
description 正是漏触发的根源。

## 测试

初始化引导是给 AI 的指令，没法自动测。可测的是 `check`：

| 用例 | 断言 |
|---|---|
| 数据源文件不存在 | 报错，指出是哪个 category 的哪个路径 |
| id 列有重复值 | 报错，列出重复的 id |
| 两个 item 产生同名输出 | 报错（构造层已有同类校验，此处提前到配置阶段） |
| 模板引用了数据源没有的字段 | 报错，指出字段名和可用字段列表 |
| 输出目录不存在 | **不报错** |
| `model` 配在 image-gen 后端下 | 报错并指向 `chain` |
| `/Game/` 前缀配 generic adapter | 报错并说明没有 unreal 适配 |
| 配置完全合法 | 退码 0，无输出或只有提示 |

## 与后续工作的关系

本次评审确定的顺序是「先做生成器」，`csv` 数据源与 `unreal` 适配排在其后。这意味着首版
`asset-config` 面对 CSV 数据源时只能报告"当前数据源仅支持 json_dict / json_list / inline"，
并建议先转 JSON —— 这是已知的临时状态，不是设计缺陷。CSV 支持落地后，初始化引导里的数据源
探测部分需要同步更新。
