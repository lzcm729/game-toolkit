## 1. 起点：现象

**A. 现在的 `book-to-reference` 还是旧流程。** 113 行，四步：评估源文件、规划文件结构、按模板写摘要、可选地整合进目标 skill。质量检查清单查的是命名、结构、行数，没有验证、覆盖审计和验收。导入稿现象 B、C 说的「引文核不了」「导入没有验收」就出在这一步。它的 description 对任何「导入这本书」都触发，默认输出位置是「当前 skill 的 references/」。

**B. 新流程只在作者本地。** 能跑通 Sylvester 的东西散在三处：

- 导入稿（在仓库里）；
- 本地约 50 个脚本：转换、核对、审计、生成、跑无界面测试、出评分包、汇总；
- 十几种子代理任务书（19 份，含各轮的副本）：阶段 0 笔记、提取、验证、复核、写卡、传播、分组、出题、评分项、盲评等。提取的任务书还要求读 cangjie 的提取器说明，并用它的索引脚本检索原文。

其中一半左右是一次性的或只用来查看。能复用的那一半里，写死了本机路径、这本书的章节分组、这本书导入过程留下的措辞替换表和几处内容裁决。不写回，下一本书（Schell 第 3 版，已定要做）要么重新摸索，要么照抄 Sylvester 专用的东西。

**C. 这一轮学到、导入稿没写的。** 每条都有实测：

1. **卡的用法要写在卡上和入口上。** 第一轮回答对比不迁移：读了卡的回答变成在复述这本书，丢了模型自己的实操内容。每张卡和选卡表开头加了一句用法，第二轮用新题通过。
2. **生成器会悄悄出错，重跑也不一定稳定。**
   - 选卡表和 notes 截长度时切进了文件名，共 5 处，原测试放过了它们；
   - 按章分组遇到平票时，结果随 Python 的字符串哈希变，重跑会把一张卡换到别的组；
   - 把导入流程的用语换成读者能懂的话，是批量替换做的，改坏了一句来源说明，还漏了二十多处「参考单元」。
   - 上面这些是 codex 三轮发版前评审陆续找出来的，不是生成时的检查发现的。
3. **验收之后的每次修改都要回归，而且两个版本要同一批跑。**
   - 口径 B 要求发布的组合就是验收过的组合。发版前评审排在回答对比之后，改了三次，每次都要重验。
   - 前两次回归拿验收版前一天的答案，比修改后版本当天的答案，按冻结判据都不通过。判差的题都对应「这次运行插件用没用上」。
   - 验收版当天重跑当对照，22 题里调用插件的次数也从 13、12 掉到 9；两天的 Claude Code 版本、模型、加载的 skill 和 agent 都相同，原因没查到。
   - 第三次让两个版本在同一批里交错跑，通过。前两次「不过」的结论原样保留。
4. **插件约一半时间不被调用，而且调用率按天变**（issue #2）。回答对比的噪声主要来自这里。
5. **成本实测**：全书提取到写卡约 1690 万子代理 token（导入稿现象 D）；接入、验收和三次回归又约 760 万；无界面运行约 108 美元 API；codex 框架复核两轮约 76 万、发版前评审三轮约 139 万 token。这些数含两轮回答对比和三次回归的试错，干净地再走一本要多少没测过。

### 要回答的问题

怎样把这套做法交给下一次导入，让它：

1. 离开作者的记忆和本地补丁，照着能做；
2. 关键检查是确定性的，生成能重跑复现；
3. 成本在开工前说得清，每一步不过就停；
4. 验收跑到实际消费方，修改后的回归不被日子干扰，也不被拿来给真退步开脱。

### 维持现行（不写回）能做到多少

- Sylvester 已经发布，不受影响。
- 下一本书照导入稿加作者本地的脚本也能做，但只有作者本人能做，而且要先把 Sylvester 专用的部分认出来、改掉。
- `book-to-reference` 继续教旧流程，它的宽触发会把使用者带进一条已经被导入稿否定的路。导入稿的停止条件也没满足。

## 4. 原则

导入稿的 9 条照旧。这一轮补 4 条，每条附「不加会怎样」：

10. **确定性生成要能复现。** 冻结的源材料、已采用的模型产物、配置和工具版本不变时，确定性生成器产出相同的发布文件；排序、平票、编码、换行用写明的规则。模型重新提取、重新写卡不承诺逐字节复现，采用的结果另行保存（「让 AI 和人都能用的软件」原则一）。
    - 不加会怎样：重跑时一张卡悄悄换了组，选卡表变了却没人改过源数据。平票那次就是这样发现的。
11. **交付给读者的文字，单独核读者可用性和语义保真。** 内部编号、流程去向、复核状态要换成读者能用的说法；换的时候不能丢掉来源性质、依据不足、适用条件和分支限制。优先在写卡时就写对，生成阶段只做明确、可复核的转换。通用措辞替换和针对某一条的内容裁决分开放，后者要能追溯。原文摘句不进措辞替换。换完用一份流程用语清单扫残留，并抽查替换后的句子；扫描只证明没有残留，不证明句意对。
    - 不加会怎样：codex 三轮评审每轮都还能找到残留；有一句被替换改坏了意思，脚本的检查全过。反过来，把「待核查」一扫了之，会把必须保留的不确定性一起删掉。
12. **改动让模型看得见的东西，就让相应的验收证据失效；重验时候选和基线同一批交错跑。** 「看得见」指入口、卡和资料、消费方指令、运行条件。只改测试实现、不进模型输入的改动，做对应的确定性验证，不触发模型回归。修复先集中做完，冻结一个候选再重验。每个新的比较批次都重跑基线的答案，但不换基线版本。同批交错减少日子带来的混淆，不消除随机性；后一次通过不改写前一次的结论。
    - 不加会怎样：两次回归都把「那天插件被调用得少」当成版本退步；反过来也可能把真退步遮住。每修一行就整批重跑，又会把成本推到最贵的那层。
13. **质量判定和归因分开。** 先盲评回答，再结合运行链路解释差异。自然链路的有效题全部按冻结规则计入，没调用、没读到、无法归因，都不把差题改成持平或剔除。没观察到某份材料被读到，只限制「这份材料的正文起了什么作用」这一归因。入口或消费链本身变差，就是插件退步。好坏对称：没读到改动材料的好答案也不算新材料的功劳。原因说不清时，按导入稿的未决或证据不足处理，不放行。强制查阅只诊断内容，不代替自然链路验收。
    - 不加会怎样：只留「两边都读了卡」的题来宣布不退步，正好删掉新版让模型少调用插件造成的损失。

## 5. 流程在 `book-to-reference` 里的样子（方向，细节进备忘）

照导入稿第 5 节的阶段和第 7 节的顺序，每一步写成「输入 → 做什么 → 产出 → 检查 → 不过就停」。检查脚本通过只说明它查的那件事成立：页码在，不等于那一页支持这一步；映射齐，不等于内容支持任务；运行文件存在，不等于这一批跑完了。

| 阶段 | 产出 | 确定性检查（脚本） | 用户确认 |
|---|---|---|---|
| 准备 | 目标是本插件源码副本（不是安装缓存），工作目录在仓库外；原书转成带页码的文本；每本书的配置 | 目标检查；页码抽查 | 胃口：按实测给全流程估价，用户拍了再开工 |
| 前置淘汰（导入稿第 7 节第 1 步） | 冻结现行版本和旧覆盖基准；宿主能加载插件副本、看得到激活和读了哪些文件；独立上下文可用；description 写得下 | 运行记录完整 | 不过就停 |
| 0 整书理解 | 逐章笔记、读者任务清单 | 任务编号唯一 | 范围和重点方向 |
| 1 提取 | 候选（方法、原则、案例、反例、术语） | 覆盖审计：每个任务都有候选，并核跨章条件 | — |
| 1.5 验证与复核 | 方法单元和去向（通过 / 只作参考 / 依据不足） | 汇总、判宽信号、复核结论写回 | 复核范围、合卡粒度（有默认就照默认） |
| 2 写卡 | 能力卡、卡片计划；每张卡带用法（第 1 节 C1） | 卡与计划对得上；摘句在标注页上；步骤带页码；复核结论传到卡上 | — |
| 3 接入与公开化 | 改名后的卡、notes、选卡表、description、消费方引用 | 引用链测试；生成可复现；流程用语残留扫描 | — |
| 4 候选内容评审（D11） | 独立评审意见和修复，冻结待验收的候选 | 同上，修复后重跑 | — |
| 5 可达与回答对比 | 独立出题、激活和读卡统计、冻结的计划、盲评、按口径 B 判定 | 评分包遮蔽检查；汇总按冻结规则；运行完整性 | 判定后的走向（导入稿 D3 三选一） |
| 6 发版 | 验收后的修复按原则 12 回归 | 同上 | 回归不过时怎么办 |

## 6. 框架级取舍（用户 2026-11-09 已拍板：全选 A）

**D7 `book-to-reference` 给谁用、产物落到哪。**

- 问题：新流程的接入、可达、回答对比都建立在「目标是本插件源码里的 `game-design-theory`」上。装了插件的使用者改不了插件里的 skill（插件更新会覆盖）。全流程一本书要两千多万 token 和上百美元 API。现行 description 却对任何「导入这本书」都触发，默认写进 skill 自己的目录。
- **已定 A：保留一个随插件发布的维护者 skill，严格收窄路由。**
  - 只接「向本插件源码中的 `game-design-theory` 导入或迁移书籍资料」这一个目标；任何改本插件源码的贡献者都能用，不只作者本人。
  - description 写正向条件和不触发的情形：普通读书摘要、整理个人笔记、导入到自己的其他 skill，都不触发。
  - 开工先确认目标是源码副本、工作目录在仓库外；安装缓存不能当交付目标，不再默认写进 skill 自己的目录。
  - 成本报价放在正文的开工步骤，description 不写具体数字。
  - 理由：真实的下一个任务是 Schell，目标就在这里；「导入到自己的 skill」现在没有已知案例（「让 AI 和人都能用的软件」原则四）。
- 备选 B：移出插件，放成仓库里的维护入口，不随插件分发。普通使用者不会误触发，但要改现有入口和分发方式。
- 备选 C：拆成「通用提取」和「本插件接入」两个 skill。多一套路由和中间交付契约，没有第二个使用者来验证。

**D8 脚本写回多少。**

- **已定 A：收主流程必需的确定性工具，保留已走通的薄运行器；`claude plugin eval` 不作为本版前提。**
  - 收的标准：主流程必需、会反复用、出错会破坏证据或交付。包括转换与核对、覆盖与去向审计、确定性生成、评分包与汇总；转换配置要靠检查源文件才能定的，配套的检查工具也收。
  - 薄运行器：两个固定插件快照的同批交错调度、记录激活和读取、标出不完整的运行。去掉本机路径和密钥位置，写明宿主要求。
  - 比较协议是我们的：独立出题、评分项、身份遮蔽、对照表隔离、口径 B 的判法。`claude plugin eval` 以后可以接替满足同一契约的执行环节，但它的默认评分不能替换口径 B，能断言调用了 skill 也不等于验过选卡、读卡和回答用上。
  - 一次性脚本不进。
  - 理由：出过错的恰恰是确定性的部分（截断、平票、遮蔽、替换），每次手写只会再错一遍；同时迁移评测平台会把本版的精力从「交接已验证的流程」分走。
- 备选 B：本版先迁到 `claude plugin eval`，手搭跑法留作后备。多一次平台迁移的验证，两种跑法都要维护。

**D9 4.19.0 本身怎么验收。**

- 问题：完整跑一本新书要两千多万 token，不在这一版里；但写回的交付物本身能不能执行，是这一版要回答的问题，不能整个推给 Schell。
- **已定 A：脚本测试、冻结产物复现、执行型冷启动。**
  - 脚本测试：用编造的小书做夹具，不放有版权的文本。能证明列出的输入、错误和边界按预期处理；证明不了各步接得上。
  - 复现：写回的生成器在作者本地的 Sylvester 工作目录上重跑，输出写到新位置，和 4.18.0 发布的卡、notes、选卡表逐字节相同。源快照和期望产物先锁住，不能边泛化边改输入或期望。能证明对这组输入行为没变；证明不了能从新书开始跑。
  - 执行型冷启动：一个没有本会话上下文的子代理，只从新 SKILL.md 出发，按链接读随包材料，用一本编造的微型书实际走通准备、提取、验证、写卡，接入插件的一份隔离副本，再把代表性产物跑到消费方（插件被调用、卡被读到）。预先放几处错误材料，验证关键的停止条件会停。仿照本仓库 `evals/asset-config-cold-start`：那里是真写配置、真跑校验，不只是问答。
  - 4.19.0 的 CHANGELOG 写明：做过执行交接验证，真实全书经验仍只有 Sylvester；Schell 验证第二本真书的适用性、质量和成本。
- 备选 B：只做脚本测试、复现和冷启动问答。便宜，但发布时没证明新流程能执行。
- 备选 C：另找一本公版书完整跑一遍。证据更扎实，也要另定胃口。

**D11 评审放在验收之前（新增）。**
