# collect-rulings：用裁决单收拍板

## 核心

裁决单只放**要用户拍的题**（游戏项目多是机制题，软件项目多是产品与工程取舍），每题不读代码也看得懂，裁决题带一个倾向（只问事实的确认题不带）；用户在页面上选，
选择以文件回到评审目录，agent 读回、复述、再落地。真值是 `裁决单.json`，页面是它的构建产物。

## 产物与位置

放在本次任务的评审目录（design-iterate 的 `docs/design-reviews/{目录}/`、
doc-consistency-check 的 `{OUTPUT_DIR}`，或用户指定的位置）：

| 文件 | 是什么 |
|---|---|
| `裁决单.json` | 题目真值，agent 写。形状见 `examples/裁决单.example.json` |
| `裁决单.html` | `scripts/build_page.py` 生成；单文件、不依赖网络，浏览器直接打开 |
| `裁决结果-<date>.json` | 用户的选择：本地路由页面下载，Artifact 路由读回后写成 |

## 一、上单之前：四件事，然后分拣

1. **核原文、记版本。** 每条「两处打架」回仓库逐字核，记文档名、节号、版本、日期。
   上游报告是从快照整理的，快照会过时；有 `doc_feedback.rulings_ledger` 就对照它，已裁过的不再上单。
2. **看工作树。** `git status` 加相关文件的 mtime。工作树不干净、或别的会话半小时内改过同一批文档，
   就等它提交再落地；它已经改掉的条目单列「别的会话已改掉的」，不再问。
3. **补代码事实。** 条目来自评审、盘点、状态机页这类没对过代码的来源时，先查每条「代码现在怎么做」
   （对账报告已经对过，不用重查）。范围按项目声明的 `source_scope`（见 layer-contracts）；
   有只读子代理就派，没有就自己查。报告里写「没有相关逻辑」不等于未实现。
   代码事实通常让一大半条目不必上单。
4. **查先例、属主的做法和受影响的全部对象。** 在本仓库和用户给的、能访问的材料里查同一个问题的现成做法，
   优先看属主的提交正文、文档和决策记录；查到就列成一个选项，或在 `ctx` 里写为什么不用，查不到写明查过哪里。
   选项要推翻属主记录过的取舍（决策记录、工程台账里的某一条），在 `ctx` 里点名。
   再按受同一行为影响的对象类别核范围和数量，逐类写这次覆盖哪些、排除哪些、为什么，不用一个样例代表整类。
   漏了现成做法或一整类对象，用户就是在不完整的菜单上选。

分拣，每条只落一档。一条里既有机制又有数值就先拆成两条再分；多行都命中取更具体的那行
（拾取动画同时命中「按代码入册」和「纯表现」，按「纯表现」）：

| 这一条是 | 去向 |
|---|---|
| 机制、规则、玩法口径：属主规格没写、和裁决冲突，或代码**有意做了另一套行为**（一段完整的新逻辑，不是漏写） | **上单**，做成选择题 |
| 提交或文档里写「按用户确认」「用户同意」，但裁决账本里没有 | **上单**：拍没拍过只有用户知道 |
| 规格没写，代码已经这么做、且只是补写 | 「按代码入册」，列进「我会顺手改的」，一行写清代码怎么做 |
| 纯数值（格数、秒数、价格、半径、倍率），只限项目让 agent 调的参数（平衡、手感这类）。把一项消耗改成 0、取消一个限制，是机制，不算数值；数字背后是产品或工程策略的（数据留多久、超时多长、配额多少），照样上单 | **agent 直接定**，不做选择题；放进「数值我定了」，每行写值和一句理由。没有试玩数据时默认取设计值，除非代码值有说得出的更好理由 |
| 规格已明确、代码**写错或漏了**（少一道检查、写错数、没接上） | 列进「直接进工程台账」（`doc_feedback.engineering_log`） |
| 文档自己前后不一致，按上下文只有一种合理读法 | 顺手改，列进「我会顺手改的」；读法不止一种就上单 |
| 纯表现（动画怎么结束、抖不抖） | 不进规则，列进「我会顺手改的」，写一句「归 Interface 层表现」 |
| 已修好、已裁过、别的会话已改掉 | 列进对应的「不在这张单上的」分组 |

这张表和 layer-contracts 的职责轴是一回事：裁决题收 Framework 规则，数值归 Content，表现归 Interface；确认题只补相关事实。
非游戏项目照用这张表：没有「纯数值」「纯表现」的就跳过这两档，「工程台账」换成项目放程序待办的地方（比如 GitHub issue）。

## 二、写题（`裁决单.json`）

- **`page.date`**＝YYYY-MM-DD；同一天第二张单加字母后缀（`2026-09-22b`），结果文件名跟着它走。
- **`page.status`**＝出单时留空；落地后写提交号与账本条目号，重建页面，页顶显示成横幅。
- **`page.intro`** 写已定方向时，写清已确认的行为或约束；待拍的部分指向具体题号（「见 E3」），
  不把已定的事又列成选项，否则读者分不清哪些已定。
- **分组按模块或属主**，不按问题类型分。组的 `owner` 写属主（`doc_feedback.owners` 里查），
  查不到写「属主未知」；先后顺序和依赖写进组的 `note`（「先拍 E1：E2 只在 E1 选 A 时才有意义」），
  不放 `owner`。
- **`title`**＝一个大白话问题（「倒地后能不能被队友拉起」）。
- **`ctx`**＝现在是什么样＋为什么要拍：玩家看得到的行为、两边各怎么说、具体数和出处名。
  **代码类名、变量名、配置键只进 `refs`**，不进标题和 `ctx`。读者没看过代码，拿不准就多写一句。
  裁决人是属主或原作者时，用对方文档和工具菜单里的叫法；和对方已有说法撞词的换掉
  （对方把进度区间叫「阶段」，就别再用「第一阶段」指工作步骤）。
  涉及可见行为差异的机制或产品取舍，在 `ctx` 写清对象、起止状态、过渡过程、时长，以及多个对象怎么先后发生；
  纯表现仍按第一节分拣。有现成截图或短片，附在裁决人能打开的交付材料里并写清看哪里；还没实现的，用文字写出各选项的可见差异。
- **`quotes`**＝两处原文，`[[出处, 原文一句]]`，逐字引、不转述；牵连到的第三处也引。
  仓库里的文件，出处写路径和行号（`物品规则.md:42`、`README.md 第 94 行`，可再带节号），
  出单时 build_page 去文件里逐字核；它只认出处里第一个写到的文件，同名文件多的仓库写全路径。
  飞书页、账本条目写名称加日期或版本（「设计账本 2026-09-22 第 33 条」），不核。
  代码那一侧没有「原文」：引提交信息或工程台账条目；都没有就引报告的转述，出处里标「转引」。
- **`facts`**＝代码现在怎么做，一条一句大白话；文件名可以带，类名、行号进 `refs`。
- **`consequence`**＝选 A 会带出什么、选 B 要删什么，一两句。
- **`opts`**＝2～3 个互斥选项，`[键, 短标签, 选了之后会发生什么, 倾向标记]`。**每道裁决题恰好一个倾向**（确认题见下）。
  第三格的第一句写成选了之后的规则句，能直接抄进账本（「倒地后 30 秒内队友按住 E 三秒能拉起，拉起后 20% 血。」），
  不写「删两处、改一句」这类动作清单，要改哪些地方写进 `consequence`。选项写对了，读回后落账本不用重新措辞。
  倾向往哪边倒：账本或属主规格有明确立场的按它；两边都站得住时倒向改动代价小的一边。
  理由在倾向项的规则句后面另起一句，以「倾向它：」开头，让用户能反驳；抄账本只抄第一句。
  倾向是给用户比的，不是替用户定的。
  开放题加一个「另定，在备注里写」。每题自带备注框，用户可以在备注里推翻选项本身。
- **确认题**：要裁决人查资产、回忆本意才答得了的事实题（「有没有部件依赖换档时重新生成」），写成
  `"kind": "confirmation"`：选项照样 2～3 个，**不设倾向**；已有证据照实引，不要求凑两处原文。
  要对方写清内容的选项（「有，备注写是哪些」）列进 `note_required`，选了却没写备注，读回时标「待补充」。
  确认题留在所属模块或属主的组里，标题以「请确认：」开头；别的题依赖它的，在组的 `note` 写明先确认哪题。
  答案回填成事实和依据，不当成规则入账。
- **`outside`**＝不上单的条目按去向分组，默认六个组名：程序已经修好的／数值我定了／直接进工程台账／
  我会顺手改的／别的会话已改掉的／其余仍开着的。项目的去向不一样就换成项目的说法，一个去向一组
  （程序待办在 GitHub issue 的写「直接进 issue」；已经先做了、有异议再改的写「这次已经按我的判断做了」）。
  组名后面可以补一句（「数值我定了（有异议回终端说）」）；没内容的组删掉。

`build_page.py` 会拦：id 重复、裁决题倾向不是恰好一个、确认题带了倾向、`kind` 不认识、`note_required` 写了不存在的选项键、
选项不是 2～3 个、缺 `ctx`、不在单上的组没内容或组名重复。
标题或 `ctx` 里疑似代码名只提醒。引文在文件里找不到、行号对不上、写的目录不对、同名文件分不清、文件读不了，
也只提醒。比对时忽略空白、全角半角、粗体和行首的引用、列表记号，原文里的「……」按分段找，CSV 按单元格原文和表格行比。

## 三、出单与交付

1. `python <本 skill>/scripts/build_page.py <评审目录>/裁决单.json` → 同目录 `裁决单.html`。
   输出最后一行是引文核对的计数。有引文提醒就逐条处理再重新 build：回原出处确认，提醒里「最接近的那行」
   和「差在」只是线索。原文还在就改回原文、改行号，或把出处写成全路径；原文确实改过了（最接近的那行是版本记录时多半如此），
   就换成现行原文，或在 `ctx` 里说明引的是旧说法。
2. 交付，二选一：
   - **有 Artifact 工具**（Claude Code）→ 按 `references/claude-code-artifact.md` 发布，给链接。
   - **没有，或用户说「出本地文件」** → 给 `裁决单.html` 的路径，用户用浏览器打开。
3. 一句话：几题、最大的是哪题；「数值我定了」有异议在终端说。然后等。

### 交给别人拍

用户要把单交给属主、原作者或同事拍时，写题前先确定裁决人和委托范围（哪几题由对方拍）。
题目照样按第二节写进 `裁决单.json`、跑 build_page 校验；下面第 3 件放在交付前，第 4 件替代上面第 2 步的交付。

1. **先读对方的东西。** 对方的提交正文、文档、决策记录。第一节第 4 件按对方的做法查，术语按对方的叫法写。
2. **写给零上下文的人。** 对方没参与讨论：`intro` 写要解决什么、已经定下的方向、这一步的范围。
   倾向注明出自谁和依据，只供对方比较。对方在委托范围内拍板；对已定方向的异议单列成「请求重开」，
   先交用户决定重不重开，决定前不替换旧裁决、不落依赖它的项。
   署名沿用用户已有的要求和目标文档的约定；用户没要求写姓名时用角色称呼，不为此中断出单。
3. **发出前冷读。** 派一个没有上下文的子代理，只给它待发的单和裁决人能看到的材料，不带本次讨论；
   先当零背景读者、再当裁决人读，读完再去裁决人的文档里核术语。交回四样：每题一句复述；
   卡住的原句、原因和改后的句子；每题能不能直接答、还是要先查什么；读完要多久。
   意见逐条核过原文再改。最多两轮：第一轮找问题，第二轮查修正和修正带进来的问题；
   还妨碍答题的列为待澄清，解决前不发。没有子代理时自己按同一清单另读一遍，并告诉用户没做独立冷读。
4. **发到对方平时看的地方。** 有可用的发布工具、项目也写明了放待议事项的位置（团队知识库的待议区这类），
   就照项目约定发布并补进那里的索引；否则交付可转发的文件，告诉用户还没发布。
   平台文档按通过 build_page 校验的 `裁决单.json` 转写，题号和选项键保持一致；题目或状态变了两边一起改。
   回复走能读到的渠道，读不到就请用户把原文贴回来。
5. **读回。** 用户要收回复时，把对方答复的原文、答复人、来源链接和读取时间存进评审目录，
   按题号整理成 `裁决结果-<date>.json`：明确的选项进 `choices`，补充或改写进 `notes`，未答留空，
   对不上选项的保留原话，不猜。然后跑第四节的读回脚本，先给用户复述表；落不落地按第四节第 4 步。

## 四、读回：第一段回复是复述表

1. 用户说「选好了」「改好了」→ 拿到 `裁决结果-<date>.json`：
   - Artifact 路：按参考文件读回，写成这个文件。
   - 本地路：用户点「我选好了」时页面自动下载它，放在评审目录；找不到就问放哪了。
   - 都没有：让用户点「复制结果文字」贴回来，存成文本文件，用 `--text` 读。
2. `python <本 skill>/scripts/read_rulings.py 裁决单.json 裁决结果-<date>.json`。
   它对不上题号、选项键或日期就退出 1 —— 那是拿错了文件，别硬解释。
3. **读到之后，第一段给用户的回复是它打出的复述表。** 归档答复原文、整理结果文件属于读回准备，可以先做；
   项目文档、代码和账本的改动都在表后。表后每个非倾向项一句「我理解为……」，每条备注一句「我读成……」。
   备注读不懂的写成问句，不猜。
4. 有未选项、「待补充」项、问句、依赖没确认，或备注改了落地范围，就停在表后等用户答。
   交给别人拍的单，不管有没有这些，都等用户明确确认后再落；其余单没有这些问题，同一轮接着落。

「用户说改好了」「计划里早写了拍完就落」「全是倾向项没什么好复述的」，都不是跳过复述表的理由。
表是给用户抓误读的机会，落地之后再抓，改回来要多一轮。

## 五、落地与收尾

1. 落地前再看一次工作树，并行会话可能刚提交或还没提交。
2. 项目写了自己的落地清单（账本追加脚本、属主页知会、摘要重推这类步骤，常在设计目录的 README 或项目 CLAUDE.md 里），
   就照清单走。没有清单，再按 `doc_feedback` 路由（四个目标的定义与读法在 layer-contracts 的「文档回填目标」一节，
   通过它的 `project_env.py check` 读）：裁决进 `rulings_ledger`，方向性问题进 `decision_ledger`，
   工程项进 `engineering_log`，属主页按 `owners`，顺带查出的代码差距也记进 `engineering_log`；
   缺块或目标不可用时只改文档、写报告，不猜账本位置。两条路都一样：「数值我定了」「我会顺手改的」照落；
   账本每条写三样：规则句（选项第三格的第一句）、取代的旧条目（没有就不写）、落地提交号。
   确认题不进账本：答到的事实和依据回填到它影响的那道题或来源页。
3. 收尾三件：把提交号与账本条目号写进 `page.status` 并重建页面（Artifact 路用同一 url 重发），
   打开页面第一眼就知道这张单已经落了；条目来源的那张页（评审报告、修正清单、盘点页、状态机页）
   按结论更新；`裁决单.json` 与 `裁决结果-<date>.json` 留在评审目录。
4. harness 有跨会话记忆的话（Claude Code 的项目记忆、Codex 的 memories），顺手记一条：
   拍了什么、落到哪、还开着什么。仓库里的账本才是真值，记忆只是下次开会话时少翻一遍。

## 常见错

| 错 | 改成 |
|---|---|
| 读到选择就直接改文档 | 第一段是复述表，改动在表后 |
| 相信上游报告里的引文 | 出处写路径和行号，让 build_page 逐字核；飞书、账本这类它核不了的回原处核；先看 HEAD 与工作树 |
| 条目来自盘点却没查代码 | 先补「代码现在怎么做」，进 `facts` |
| 裁决题只有 `ctx` 没原文 | 两处原文进 `quotes`，代码事实进 `facts`；确认题的证据要求见第二节 |
