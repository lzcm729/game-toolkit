# 讨论设计的默认方式

## 12. 先结构后内容；规格只写客观动作

这一条来自插件作者讨论设计时的习惯，作为默认方式。用户另有偏好时照用户的；具体口径以项目裁决为准。

- **先讲结构层。** 机制怎么运转、系统接口、规则边界先讲清；具体内容举一两个例子就够，交互细节不问就不展开。
- **问题排序。** 按「结构冲突 > 内容缺口 > 表现打磨」排；数值归在内容层，不单独列一层。
- **先写体验目标。** 每个方案开头先写一句这次改动想带来的情感体验。
- **先分清信息的性质。** 项目还没裁定反馈方案时，对预测线、建议、告警色逐项判断它表达的是状态事实、结果预测还是策略推荐；只对会改变玩家信息条件或决策责任的方案，拿出来和用户确认取舍，不直接做成默认。项目已经裁定要做的（比如某个倒计时），照项目的来。
- **不压缩用户的决策空间。** 不拿「一键更方便」或「有涌现的机会」来压缩选项。
- **说不清哪里不对。** 用户说「不对，但说不清哪里不对」时，先查是不是和旁边某个概念抢了语义地盘。
- **规格只写能客观判定的动作。** 玩家口语里的概念（偷、恶作剧）要改写成程序能判断的表述，比如「能不能被交互」；参与者的主观意图不写进规格。
- **将来要整体重做的系统**（存档、键位这类），现阶段按现状认，不为它新增规则，也不打磨细节。
