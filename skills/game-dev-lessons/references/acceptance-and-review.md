# 验收与评审

## 10. 游戏侧的验收

- **验完整的消费链。** 新增的状态字段、配置项、效果，要验：声明、存储、计时、至少有一处读取并改变了行为、玩家看得见（界面能到达、生效后有反馈）。写进去不等于生效，日志说生效了也不算；同名字段读的可能是另一个对象；只在模拟一端有消费的，是危险信号。
- **按感知通道选测量方式。** 直接调逻辑，能证明数值和算法；真实场景启动，能证明装配、信号和生命周期；截图能证明看得见；真人试玩才能证明涌现类假设。不要为了凑测试去强改自动代理。
- **截图里看不到东西时**，先查组件是不是被叠住、是不是默认隐藏、默认数据是不是空的，最后才怀疑渲染。
- **平行路径一起改。** 改规则或表现时，查一查有没有平行的第二条路径（无头模拟器、截图渲染、数值脚本），要一起改。
- **可复用组件不自带位置。** 可复用的子场景、组件、预制体，根节点不自带位置和层级，放在哪里由使用它的一方决定。

## 11. 设计评审与试玩的节奏

- 大改动或新系统上线后，一两轮之内就要实际玩一次；重大重构合并后的第一次试玩，专门用来验证根因是否真的解决了。
- 用最差或最极端的玩法去暴露隐藏问题。
- 评审时轮换不同的玩家人设，多种策略各跑一遍，比同一种策略跑很多遍更有用。同一人设反复回访，大约 5 轮就饱和了。已知问题清单变长以后，只传问题类别。
- 待办清空时就去玩，不要没事找事。
- 审设计文档时，文档质量标准和设计评审视角各查各的，不能互相替代。
- 判定条件只能依赖玩家看得见的信息，否则失败无法归因。「A 和 B 都可以」等于没设条件，要改写成真正被排除的情形。
