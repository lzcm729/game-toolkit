# asset-config — 建立与维护项目的资源配置

`asset-config.yaml` 描述「这个项目有哪些资源、从哪来、长什么样、生成到哪去」。
字段说明在 `../generate-assets/examples/README.md`，本 skill 管的是**怎么把它建起来**。

## 为什么需要这份指引

字段多，其中一部分必须由人决定 —— 而 AI 有个天然倾向：看到候选值和默认值就自己填了。
这不是假设，是实测。咨询另一个 agent 时它自己的原话：

> 我不会天然把清单里的每一项都理解成必须问人。如果里面同时给了候选、依据和默认值，
> 我可能判断其中一些已有足够证据，直接采用。

所以下面每个字段都标了**决策权限**。看到「必须询问」就是真的要问，**推荐值不等于答案**。

## 流程

```
读项目声明与实际结构
  → 提出带依据的草稿
  → 只问真正未决的缺口
  → 写带注释的 yaml
  → check
  → 出小样迭代
```

**「带依据的草稿」是关键**。不是复制一份示例让用户填空，而是你已经读过这个项目、
知道它的数据在哪、美术源目录叫什么、用的什么引擎，然后给出有理由的具体值。

## 决策权限三档

| 档 | 含义 |
|---|---|
| **可推断** | 有充分项目证据就填，**并说明依据是什么** |
| **必须询问** | 没有现成的用户决定就必须问到答案。**推荐值不等于答案** |
| **可暂留** | 先写草稿，标 `TODO`，之后迭代 |

三条规矩：

- 用户之前已经做过的决定可以直接复用，不必重问。**证据去这些地方找**：项目的环境
  声明、数据表自带的结构声明（sidecar）、已有的同类配置、以及明确记录下来的裁决。
  复用时交代来源和它管到哪 —— 不同来源打架时才需要问人
  （注意这只是常见的几处，不是说每个项目都必然有其中某一种）
- 用户说「这些你定」也算授权
- **没问到答案的，不能登记成「用户选择了默认值」**

### 把来源写进配置

「必须询问」档的字段，在生成的 yaml 里**必须在紧邻的注释里写明值从哪来**，
格式是固定前缀 `来源：`：

```yaml
# 生图后端。laozhang 随插件安装，需要 LAOZHANG_API_KEY
# 来源：用户选定（候选 image-gen / laozhang；本项目没装 image-gen）
backend: laozhang

      # 来源：沿用 Knowledge/Schema/鱼表格.yaml 的 identity_column 声明
      id_column: fish_id
```

`check` 会强制这一条 —— 缺了就指出是第几行的哪个字段。

**但它报的是「治理问题」，不是运行错误。** 缺注释的配置照样能正确生成图片；
格式化工具重排 YAML、删掉注释就会触发它，而运行语义一点没变。所以两者分开：

| | 含义 | 退码 |
|---|---|---|
| 运行合法性 | 会让生成失败，或产出错的东西 | 1 |
| 配置治理 | 能跑，但意图没被声明过 | 3 |

治理这一档只收一类问题：**「必须询问」档的字段没写来源**。它的判断依据是
注释，而注释不影响运行——格式化工具删掉注释，这档会失败，运行语义一点没变。

（数据列撞名当生图参数用那件事，4.0.0 起归运行合法性：配置的行为不该依赖
没人声明过的巧合，和后端丢掉一个声明过的字段是同一类问题。）

**交付这份配置时要求两样都过**（`check` 缺省就是两样都跑）。但下游消费者
可以只要一样：`--check runtime` 只看能不能跑，`--check governance` 只看有没有
写来源（纯读注释，数据源和工程不在位也能跑）。否则每个未来的消费者都要被迫
继承某个 agent 写配置时的交互规矩。

**它挡不住一个决心撒谎的 AI**（注释是你自己写的），但挡得住「顺手填了忘了问」，
而后者才是实际会发生的那种。顺带让配置本身成了可审查的决策记录：半年后有人翻开
这份 yaml，能看出 `model` 是问过人的、还是谁随手定的。

写「沿用某处的声明」同样算来源 —— 要求说清的是**从哪来**，不是证明**问过谁**。
后者任何静态检查都做不到，别假装做得到。

## 怎么问

有结构化提问能力（能弹选项让人选）就用它；没有就在回答里编号列出。两种方式都必须给出
**候选值、每个候选的理由、以及自己填的余地**。

不要依赖卡片长什么样、一次能问几题、答案是不是同步回来的 —— 不同的 agent host 差别很大，
按最低能力设计。

**先定要什么能力，再挑后端和模型。** 顺序反了就会出现「选完才发现不兼容」：

```
需要什么能力  →  backend  →  model / chain  →  aspect_ratio
```

第一步要先问清楚：**要不要多图风格锚（reference_paths）？要不要基于一张底图编辑
（image）？** 这两个能力不是所有后端/模型都有 —— 比如走 OpenAI 路径的模型没有多图
参考。先确认需求，再拿它去筛候选；不要先定模型再回头发现风格锚用不了。

具体哪个模型支持什么，别在这里维护一份会过期的表 —— 让 `check` 去判（它复用后端
自己的能力判断），字段说明见 generate-assets 的 examples/README.md。

**注意这条链上的每一环都影响下一环**：

`image-gen` 用 `chain` 表达模型选择、根本不认 `model`；后端还决定了比例有哪些档位
（OpenAI 路径只有 1:1 / 2:3 / 3:2）和能不能用多图风格锚（OpenAI 路径不能）。
先定后端，再问模型，最后才谈比例。

## 各字段的决策权限

| 字段 | 权限 | 怎么定 |
|---|---|---|
| `adapter` | 可推断 | 读 `game-toolkit.yaml` 的 `engine`；没有就看有没有 `project.godot` / `*.uproject` |
| `output_root` | 可推断 → 确认 | 见下方「输出目录不只是挑个文件夹」 |
| `data_source` | 可推断 → 确认 | 扫到的 CSV/JSON。**哪份代表待生成资源必须人确认** —— 项目里的表可能有十几张 |
| 数据源的 id 列 | **必须询问** | 你能报「哪些列唯一且无空值」，选哪列是人的决定 |
| `backend` | **必须询问** | 取决于用户装没装 image-gen、愿不愿用插件自带的 laozhang |
| `model` / `chain` | **必须询问** | 依赖 `backend`，见上面的顺序依赖 |
| `aspect_ratio` | **必须询问** | 依赖用途（图标 / 立绘 / 背景），而且会随构图迭代 |
| `prompt_template` | 可暂留 | 你写第一版草稿，人在小样里迭代 |
| `style.prompt_prefix` | 可暂留 | **不强制非空** —— 风格可以写在 category 里，或用 `skip_global_style` 关掉 |

## 输出目录不只是挑个文件夹

`output_root` 看起来只是选个目录，实际要同时满足三件事，缺一件都会在后面咬人：

1. **谁来消费这些图**。顺着项目现有的导入/打包脚本看，它们从哪个目录读、按什么命名规则
   找文件。生成出来的东西要能被下游认领，否则就是一批没人用的图。
   —— 顺带核对一件容易漏的事：**数据源的 id 列同时也是输出文件名**。它是表的身份列，
   和它是否符合项目的资产命名约定，是两个需要分别拿证据的事实。
2. **版本控制状态符合项目约定**。推导出本批**预期的文件路径**（id + 输出子目录 + 扩展名），
   核对它们会不会被忽略规则挡掉。注意逐文件白名单很常见 —— 同一个目录里旧文件被跟踪、
   新文件被忽略完全可能，**「目录里已经有一堆图」不能当作安全的证据**。
   源图该不该入库因项目而异（有的项目只管导入后的资产），所以这是要**确认**的事，
   不是可以替用户定的事。
3. **和已有的同类产物放在一起**。项目里常有不止一个美术目录，职责分工未必写在文档里，
   得从谁在写它们、写进去的是什么来判断。

## 开放题：问目标，不问成品

`prompt_template` 和全局风格是自由文本，**而且必须反复迭代** —— 实测一张图的 prompt 要改两三轮
才对。向导式地问一次「你想要什么风格」，只会得到一句敷衍，人最后还是回编辑器改。

但这不等于不问创作意图。该问的是**用户答得上来的目标与约束**，由你转成模板：

- 这批道具是小尺寸背包图标，还是大幅展示插画？
- 角色要俯视、侧视还是正面？
- 沿用项目现有美术（有参考图吗），还是探索新风格？

这些直接改变构图和模板结构。「可爱 / 像素 / 赛博朋克」这类风格词可以辅助，但不足以定出
一个能用的游戏资源模板。

然后**由你写出引用真实数据字段的第一版**。不让用户从空白开始写，也不要声称这一版就定稿了。

### 顺手把验收条件定下来

问完目标，趁着还记得，把答案整理成**几条能看着图对照的具体条件**。「首张定方向」要求你
做判断，判断依据就得在这时候立好，否则看到图只能说「好像还行」。

下面是**维度**，不是条件本身 —— 每条都要填成这个项目的具体要求才有判断力：

| 维度 | 填成什么样才管用 |
|---|---|
| 风格继承 | 参考图里到底要继承什么：配色？轮廓简化？面片感？材质？光照？——「颜色接近」不等于风格继承了 |
| 构图与用途 | 朝向、主体是否完整、占画面多少。用于小图标的还要看缩到实际尺寸还认不认得出 |
| 背景 | 允许有场景、要求单色、还是要透明。「干净背景」不够精确，也不等于透明底 |
| 比例与尺寸 | 实际输出和使用位置对不对得上 —— 比例合法不代表主体摆得合适 |
| 条目差异 | 第二张既要保持同一方向，又要体现数据里本该影响外观的差异。全都只是换个颜色就说明模板没吃到数据 |

用不上的维度不要硬凑。

**谁来判断也要分清**：明确写下来的约束（背景要单色、必须侧视）你可以自己对照；
审美方向满不满意是用户的事 —— **「图已经出来了」不等于「用户认可了」**。
没过的条件要指名道姓说出来，然后回去改模板，不能因为 `check` 是绿的就进批量。

## 数据源的列可能意外控制生成

真实的数据表不只有内容，它的列名可能撞上生成参数。如果表里恰好有 `model`、`image`、
`aspect_ratio`、`seed` 这些列，它们会成为 **item 级**参数，**优先级高于 category 配置** ——
在 category 层写同名字段压不过它们。

所以出小样时要核对**最终实际生效的参数和完整 prompt**，而不是只看 yaml 里写了什么。
画面不对的时候，先确认送出去的输入符合预期，再判断是措辞不够还是模型没听。

具体哪些字段有这个性质，看 generate-assets 的 `examples/README.md`，别在这里另记一份。

## 两类「未完成」要分开

| 类型 | 例子 | 怎么处理 |
|---|---|---|
| **功能性缺失** | 模板引用了数据源里没有的字段 | `check` 报错，必须修 |
| **创作性未定稿** | 能出图，但风格还没满意 | 标 `TODO`，`check` 只提示 |

混成一个「TODO」的后果是：要么人忽略了真错误，要么被没定稿的风格卡住不敢跑。

## 校验

```bash
python <本 skill 目录>/scripts/check_config.py --config <配置路径>

# 只看能不能跑 / 只看有没有写来源
python <本 skill 目录>/scripts/check_config.py --config <配置路径> --check runtime
python <本 skill 目录>/scripts/check_config.py --config <配置路径> --check governance
```

`--project-root` 只在要**覆盖**本次校验的工程根时才给。不给的话它按和生成器
完全相同的规则去定（config 的 `project_root` → 适配器探测 → 按 config 位置推断），
并把用了哪一条打在提示里。**这个根定在哪，所有相对路径就以哪为基准** ——
输出目录、参考图、数据源全挂在它上面，所以它值得被看一眼。

它查这些：

- 数据源能不能加载；id 有没有缺失、重复；会不会产出同名文件
- **每个条目的模板占位符都能渲染** —— 不是抽第一条，也不只是 YAML 语法对
- 每张图最终落到哪个文件；`output_subdir` 有没有越出 `output_root`
- 路径解析与后端能力相容（`/Game/` 配 filesystem、`model` 配 image-gen、
  走 OpenAI 路径的模型配多图参考这类；能力由后端自己声明）。
  **丢掉会改变结果含义的字段算错，不是提示** —— 要降级跑就加 `--allow-degrade`，
  生成器有同名开关，两边判断一致
- 还剩哪些 `TODO` 标记

两条边界值得知道：

- **输入图片必须存在**（风格锚、编辑底图），但**输出目录不存在不算错** —— 生成时会自己建
- 退码 0 表示**这份配置的静态部分自洽**，不等于「整批都能跑通」，更不等于「画面对」。
  已知覆盖不到的：后端脚本没就位只给提示不报错；凭证、网络、模型是否听话，
  以及生成的画面像不像 —— 这些只有出小样能回答
- 退码有三个值：`0` 全过 / `1` 运行合法性有错 / `3` 只有治理问题（见上面「把来源写进配置」）。
  `1` 和 `3` 分开，是为了让消费者不必解析文本就能分辨「跑不了」和「没留决策记录」

**它和生成器算的是同一个计划**：同一份上下文解析（`asset_context`）、同一份
计划构造（`asset_plan`）。不是"复用几个底层函数"，是同一条链走到底 ——
所以 check 看到的 prompt、落盘位置、生效参数，就是真跑时的那一份。

## 完成条件是小样，不是 check 通过

`check` 能确认模板渲染得出来，确认不了画面符合预期。真正的验收：

```bash
# 先看 prompt 对不对，不花钱
python <generate-assets>/scripts/generate_assets.py --config <cfg> <category> --dry-run

# 再出一两张真的
python <generate-assets>/scripts/generate_assets.py --config <cfg> <category> --limit 1
```

`--limit N` 取前 N 条，不用先去数据源里查 id；要挑特定的几条用 `--names`。

**首张定方向，再换一个差异较大的条目验模板能不能泛化。** 比如角色 category 里，先出一个
体型正常的，再出一个体型极端的 —— 模板里写死的构图假设会在第二张上露馅。

这一步比继续追问更有用：prompt 的问题只有看到图才说得清。
