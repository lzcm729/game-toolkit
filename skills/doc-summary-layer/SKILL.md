# doc-summary-layer — 仓库详稿，平台摘要

**一句话**：设计文档只有一份真值，在仓库里；平台上的页不是副本，是给人看的摘要。

**为什么不是镜像**。把仓库正文整页发布到平台看起来最省事，实际会出三件事：平台页上的原生对象（内嵌表格、评论、协作痕迹）被覆盖掉；读者看到一页完整正文就把它当真值，改在上面的东西不会回流；两边只要有一次没同步，"以哪边为准"就成了每次讨论的开场白。**摘要不承诺一致**，这正是它能长期活下去的原因：它只负责让人在一屏内建立正确的心智模型，判定细节、数值与出处一律回仓库看。

---

## 两层各是什么

| | 详稿（SSOT） | 规则版摘要 |
|---|---|---|
| 放哪 | 仓库设计目录，走 git | 阅读平台，每份详稿对应一页 |
| 谁读 | 实现者、对表与一致性工具、审核者 | 全体成员，尤其不读仓库的策划与美术 |
| 谁改 | 属主，改动即提交并记版本行 | 详稿大改后由人重写、整页替换；平台上的手改不回流 |
| 内容 | 完整机制、判定条件、数值出处、版本表 | 一句话画面 ＋ 按机制群分组的规则句 ＋ 接口 ＋ 未决 |
| 承诺 | 真值 | 标明日期与仓库版本，不保证同步 |
| 工具读不读 | 读 | **不读**——摘要不进对表范围，也不当要求来源 |

摘要放哪由项目定：可以只在平台（仓库不存，重写时从详稿再提炼），也可以在仓库里一个**明确排除在工具范围外**的目录（能重推、能 diff）。两种都行，别把它放进设计目录——它不是经过审核的设计文档，混进去会被对表工具当成第二份要求。

---

## 三条数据流

改错地方的后果是被覆盖或被忽略，所以先定方向再动手。项目应把这三条写进设计目录的 README。

### 一、正文：在仓库写，摘要往平台发

详稿直接改仓库文件、走提交。平台同名页只放摘要；详稿大改（口径变、结构重排）后重写摘要并整页替换。摘要里的数值一律标「快照」或「参数页为准」，不承担出处。

### 二、内容表：两边都能改，以仓库为准

策划在平台表格里填值、定稿后拉进仓库；裁决改表可以直接改仓库那份。两边不一致时仓库是真值。**拉取者负责先回写再拉**：先看仓库这张表自上次拉取后有没有改过，改过的先回写平台，再整张拉，不能直接覆盖。清单里保留平台的版本号只作「资产是否落后于表」的信号。

### 三、草稿、任务板、点子、账本：只在平台，审核通过才迁入

在平台起草是正常路径，不是风险：策划案、方案、点子先在平台写，属主与负责人审核，**通过审核才迁入仓库成为真值**。没迁入的不算现行设计，工具不把它当要求读。属主待办页、程序待办页、交接页、点子库、排期这类不是设计文档的页只在平台，仓库不放它们的快照。裁决账本放哪是项目选择：放仓库便于工具引用，放平台便于全员追加；无论放哪只能有一份完整版。

**迁入步骤**：导出 Markdown → 补 front matter（真值标记、平台页身份、迁入时的平台版本）→ 登进清单与工具配置 → 刷新内容哈希 → 平台原页换成摘要（或先挂横幅指回仓库）。

## 摘要规格

一份摘要就是一个 Markdown 文件，按详稿的相对路径命名，结构固定：

```markdown
# 一句话

<用一句形象的话说这份文档管的是什么因果；不含从句、不带阈值>

# 规则

## <机制群一>

- <一条规则一句话，主语＋判定＋结果>
- <…>

## <机制群二>

- <…>

# 接口            （可选：这份文档向外要什么、给什么，一条一个来源或去向）

- <…>

# 未决            （可选：详稿里明确写着待定的事，不替它拍）

- <…>
```

**写作规则**（检查脚本能查的都在 `scripts/check_summaries.py` 里）：

- 每条规则是完整的一句话，约 60 字内；写不进一句就是两条规则，或者它属于详稿不属于摘要。
- 只用一级标题、二级分组、无序列表；**不用加粗、表格、嵌套列表、引用块**——不同平台对这些的解析差异最大，也最容易在整页替换时变成字面字符。
- 现行真相才进摘要：废案、旧词、已作废的口径一个都不露面。项目维护一份死概念词表交给检查脚本。
- 数值写快照并标明（「快照」「参数页为准」），不写出处链接——出处在详稿。
- 「一句话」按读者要建立的因果认识写，不按标题逐条铺；比喻不得与机制相悖。
- 「未决」只转述详稿里已标待定的事，不把摘要作者的疑问混进去。
- 摘要不记版本表；日期与仓库版本由横幅承担。

**规模感**：一份 300～800 行的详稿通常压成 30～100 条规则；超过 120 条多半是把判定细节搬进来了。

**质量兜底**：检查脚本只能查结构与词表，查不出「规则写反了」。摘要由子任务或他人批量提炼时，发布前对每份抽 3～5 条与详稿逐字核——这一步不能省，批量提炼的常见错就是把上一版口径写成现行。

## 横幅

每页第一块是一条引用，告诉读者这是什么、多旧、真值在哪：

```
> **规则版摘要**（{date}，据仓库 {rev}）。本页帮你快速建立心智模型，不保证与仓库同步；判定细节、数值与出处以仓库 `{ssot_root}/{file}` 为准，改设计只改仓库。
```

三个占位由构建脚本填；`{rev}` 是发布时的仓库版本（短 hash 或版本号）。横幅只说这三件事，不在这里放流程说明、意见渠道之类会过期的话。

---

## 清单（manifest）

一份 JSON 把详稿文件与平台页身份对上，工具与适配器都读它。最少三个字段：

```json
{"docs": [{"file": "GDD/钓鱼系统.md", "node_token": "<平台页稳定身份>", "content_sha1": "<详稿内容哈希>"}]}
```

- **平台页身份不得更改**——它同时是对表工具稳定要求键里的文档身份，改了整份基线对不上。
- 内容哈希由仓库文件算，用来判断哪些系统要重跑对表；平台的版本号只作溯源。行尾（CRLF／LF）会改变哈希，算之前归一。
- 清单只列详稿；摘要按同一相对路径找，不另登记。

## 工作流

```
详稿大改（口径变／结构重排／成稿）
    ↓
重写这份摘要（人写；批量提炼后抽查 3～5 条）
    ↓
python scripts/check_summaries.py --summaries <摘要目录> --manifest <清单> --dead-words <词表>
    ↓
python scripts/build_summary_pages.py --summaries <摘要目录> --out <输出目录> --manifest <清单> --rev <仓库版本> [--profile <平台>]
    ↓
项目侧适配器把输出目录里的页发到平台（整页替换正文，保留原生对象）
    ↓
回读验证：标题数、关键句、有没有字面标记残留
```

**适配器契约**（项目侧实现，语言随项目）：

1. 输入：构建脚本的输出目录 ＋ 清单；按 `file` 找到平台页身份。
2. 只替换正文块，**保留页上的原生对象**（内嵌表格、附件）；做不到就先把原生对象单独摘出来、只删正文块再插入。
3. 标题不动；覆盖前先取一份当前页面存档；覆盖会丢评论，要在流程里说明。
4. 发完回读同一页，核标题数与几句关键句；返回平台版本号供记录。
5. 一次只动清单里的页，不碰属主页、任务板等只在平台的页。

平台 profile 决定构建脚本做哪些标记修正（比如飞书要把加粗改成 `<b>`、表格单元格里的加粗去掉）。新平台先按 `plain` 发一页试，回读看哪些标记变了字面字符，再给它建 profile。

## 陷阱 checklist

- [ ] **整页镜像**：把详稿原文发上平台。后果是原生表格被复制品顶掉、评论丢、读者把副本当真值。整页替换只用于摘要，且要保留原生对象。
- [ ] **摘要进了工具范围**：摘要文件放在设计目录或对表配置的 docs 范围里，工具把它当第二份要求。放平台或放排除目录。
- [ ] **横幅没日期没版本**：读者无法判断多旧；一旦有人据摘要做决定就会追问哪边对。
- [ ] **死概念**：摘要提炼时顺手带进了旧口径；同批必扫详稿——今天在摘要里翻出的旧词，多半详稿里也还有一处。
- [ ] **批量提炼不抽查**：结构全过、词表全过，规则却是上一版的。
- [ ] **平台标记差异**：加粗贴着全角标点、表格单元格加粗、跨行加粗、被段落隔开的有序列表——每个平台各有几种会变字面字符或重编号的写法，第一次发新平台先试一页再批量。
- [ ] **清单身份被改**：为了整齐改了平台页的身份键，对表基线整份失效。
- [ ] **在平台上改摘要**：改了也不回流，下次替换就没了；改设计只改仓库。

## 与其他 skill 的关系

- `sync-docs-ahead` / `doc-consistency-check` 只读仓库详稿；本 skill 保证摘要不进它们的范围，清单里的页身份就是它们的稳定键。
- `split-doc-layers` 按职责拆详稿，本 skill 按读者拆出摘要；一份详稿可以既拆职责又出摘要。
- `design-discuss` / `design-iterate` 的产物落到详稿；落完再重写摘要。
