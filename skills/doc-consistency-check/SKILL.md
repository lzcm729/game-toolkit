# 设计文档一致性检查

对多份设计文档做交叉比对。分组提取后，三个镜头各读全部结果，再合并、逐条复核，
最终给出能打开两边引证检查的报告与修正清单。

## 工作流程

### 1. 扫描文档

通过 `layer-contracts` 的 `scripts/project_env.py check` 读项目根 `game-toolkit.yaml` 的
可选 `doc_feedback`。路径相对声明的 `project_root` 解析，主流程将配置及来源传给各 agent。
缺块时只写报告、不路由；缺某个目标就跳过该路由；已配置但不存在则报告该目标不可用，不能猜路径。
任务文档清单沿项目声明或其指向的文档索引取得，输出位置记作 `{OUTPUT_DIR}`，由本次任务指定。

扫描目标目录所有 `.md` **和 `.csv`**，内容表也是文档。排除依据是**文档自己声明的状态**，
不只看归档目录名；归档页排除并列清单。文件名或首行带「已废弃」「勿引」「旧版」「Demo 不做」
「候选」「不是 SSOT」的默认排除。`doc_feedback.exclude_markers` 若给出则整组覆盖默认清单，
空列表有效。正文「版本记录／修改记录」段只作溯源，不当现行定义。
页头自标「草稿」的页保留供比较，但单独提取、单独报告，不与现行页混列。

有 `doc_feedback.rulings_ledger` 时读裁决账本，按日期最新为准；已建专表的数值以专表为准，汇总页只留依据。
其余页面的权威关系从项目声明和文档自身指针取得。具体页面、属主、日期不能写死在 skill 中。

### 2. 分组

按主题分成适合上下文容量的组，相关文档同组、负载均衡，边界概念留给跨组比对。
系统入口、子规格与 CSV 都在分组清单中，不因表格不是 Markdown 而漏掉。
**交互模式下先展示分组方案并确认；自动模式下把分组方案写进报告头后启动。**
自动模式可由用户明确指定；不因等不到回答自行切换。

### 3. 阶段1：并行结构化提取

每组一个 Explore agent（`run_in_background: true`），使用本 skill 的
[references/extraction-prompt.md](references/extraction-prompt.md)，只提取不评价。
若提取结果需落盘，则由主流程写入或使用具有 Write 的子 agent，不能要求只读工具集写文件。
每组按六个维度提取：数值定义、概念定义、流程与规则、枚举列表、组内矛盾、模糊/未定义。
每条都带来源定位：Markdown 用文件:行（含 frontmatter），CSV 用文件＋第 N 行＋列名，
不写列字母。有 revision_id 的文件在首次引用时附版本。逐页通读，CSV 逐行读，空值不当零。

### 4. 阶段2：三镜头交叉比对

全部提取完成后，并行启动三个交叉比对者，各读**全部组**的提取结果；
按本 skill 的 [references/cross-lenses.md](references/cross-lenses.md) 分别执行：

- 数值与枚举：数值口径、概率基数、枚举成员、专表与汇总页。
- 术语流程接口：名称、计数方向、步骤顺序、状态转换、跨系统参数、裁决残留。
- 跨组数值机械扫描：合并全部数值定义，同义词按来源语义归并，逐概念列出不同值。

同时使用 [references/cross-reference-checklist.md](references/cross-reference-checklist.md)。
三个镜头均输出 findings 和 checked_ok，后者记查过无问题的概念，供检查覆盖面。
主流程合并去重：**同一对引文只留一条，引证更完整者优先**，分析可合并各镜头观点；
同一概念不同引文对不能硬合并。引文对不区分左右顺序，按文件、定位、原文核对身份。
保留合并掉的标题与来源镜头，按高→中→低、同级按文档路径排序，统一编号 C01、C02…。

### 4b. 阶段2b：复核

每六条分配一个独立复核者，末批不足六条照常复核，使用本 skill 的
[references/verify-prompt.md](references/verify-prompt.md)。打开两边引证，行号容忍 ±3 漂移，
找不到就 Grep 原文；有 `doc_feedback.rulings_ledger` 时查是否已有更晚裁决覆盖，
并判断同名异义、不同阶段或总览与规格粒度差异。
verdict 只允许：成立／不成立／已被裁决覆盖／降级／升级，每条带最终严重度与实际证据。
已裁但页面未改的仍是「残留」，不能因有裁决就淘汰；已裁且页面同步的才按复核规则淘汰。

有 Workflow 工具时按提取并行→三镜头并行→合并→分批复核→报告编排；没有时后台子 agent
按相同依赖顺序推进，并发上限按环境。缺提取组或镜头时先补齐，不能将部分覆盖报成全量检查。
复核未返回的保留并标「未复核」，不计入已成立总数，也不把它当已淘汰；主流程明确未完成范围。
零发现也写报告，列分组、排除清单和 checked_ok，不直接静默结束。

### 5. 生成报告

主流程或报告撰写者将结果写到 `{OUTPUT_DIR}` 下的本次报告文件。页头记录本次文档版本或
导出时间、分组方案（每组完整清单）、排除清单、方法、覆盖面与未完成范围、提取产物位置。
采用复核后的严重度：高＝数值/规则直接矛盾且影响实现；中＝术语残留、定义分散、接口未对齐；
低＝格式过时或不影响实现的缺失。没有双侧引证的泛泛缺文档建议不进冲突清单。

正文格式：

```markdown
## 矛盾 {C编号}：{简短标题}

**现状：**
| 来源 | 定位 | 原文 |
|---|---|---|
| {文档} | {实际定位} | {引文} |
| {另一文档} | {实际定位} | {引文} |

**分析：** {为何矛盾，裁决日期及复核 evidence}
**建议：** {具体修正动作与依据}
**严重程度：** {高/中/低}
**复核：** {verdict 或未复核}
**负责人：** {从 doc_feedback.owners 读取；未配置则未知}
```

正文后必须另列两节：

- **草稿冲突**：页头自标草稿与现行页的差异单列，保留两侧引证、复核结果、最终严重度；
  需要属主判断改现行还是改草稿，不混入现行文档矛盾计数。
- **复核淘汰**：备查所有「不成立」「已被裁决覆盖」条目，保留原 C 编号、标题、理由与证据。

两节无项也写零。淘汰条目不再进入修正清单；降级／升级按最终严重度排列。
`doc_feedback` 缺块时仍完成报告，不能为了找回填目标而阻断检查。

### 6. 逐条过审与输出

将需要设计判断的条目呈现给用户，记录同意／修改／搁置。交互模式逐条过审；自动模式先输出
带空白裁决列的完整待审清单，不代用户做设计裁决。修正清单格式：

```markdown
| 编号 | 问题 | 修正动作 | 改哪个文档 | 负责人 | 需属主判断？ | 用户裁决 |
|---|---|---|---|---|---|---|
| {C编号} | {问题} | {动作} | {目标定位} | {属主或未知} | {判断/机械} | {裁决或留空} |
```

有属主表时按属主分组。机械项＝改状态字段、加版本行、按已定词表替换术语、删已判死的残句等
不需要设计判断的动作；修正依据必须已有明确裁决，选哪套规则或改哪个数值仍是「判断」。
检查流程只写报告和清单。用户已授权执行修正时，执行者可直接做机械项并知会属主，
不用逐项再求设计裁决；未授权发送消息时把知会内容写在交付里交用户转达。
方向问题可标注 `doc_feedback.decision_ledger` 为回填候选，执行状态可标注
`doc_feedback.engineering_log`；本轮不直接修改任何项目账本，是否回填由主流程与用户决定。

## 注意事项

- 现行页、草稿、归档及历史段分别处理，不能因版本行提过旧数值就报现行冲突。
- 提取只整理双侧事实，不评文档质量；判断由三镜头和独立复核完成。
- 不因只有一处定义就报矛盾；未定义问题需两页对同一缺口给出冲突暗示才进入比对发现。
- 不修改设计、镜像或源码，只生成报告与修正清单；后续执行依用户已有授权。
