# 试玩协议与测试者

> **怎么用这张卡**：它是方法和书中依据的来源之一，不是回答的模板。回答围绕用户的处境：先给你自己的专业判断和具体做法，书外的实操（算一个例子、查数据、估成本）照常给；再用这张卡补方法、校正判断。不要按卡的分段复述这本书；卡里没写的，不等于不能答。书名和页码只在用户要出处时给。

## R — 原文 (Reading)

> A TEST PROTOCOL is a set of rules and procedures for carrying out a playtest.
>
> 译：测试协议，是实施一次试玩的一套规则和程序。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / Test Protocol, p.295

> Creating a good test protocol is hard because there is no feedback when we do it wrong. … Worse, bad test protocols usually make tests go more smoothly, not less.
>
> 译：好的测试协议难做，因为做错了没有任何反馈。……更糟的是，坏协议通常让测试进行得更顺，而不是更不顺。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / Test Protocol, p.295

> There’s no one number of playtests that are needed for this. … A good rule of thumb is to stop playtesting when you start seeing testers repeating the same experiences often.
>
> 译：要测多少场，没有一个统一的数。……一条好用的经验法则是：开始常常看到测试者重复同样的体验时，就停测。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / Sample Size, p.299

## I — 方法骨架 (Interpretation)

这张卡回答「一次试玩要定哪些规则、找谁来测、测几场才够、这次测试的设计有没有毛病」。测试是迭代从现实里学东西的那一步，测试协议（test protocol）就是实施一次试玩的规则和程序。作者的道理是：协议做错时不会报错，被污染的结果看起来很合理，坏协议还往往让测试更顺；测之前设计者知道自己不知道，测完反而以为游戏行了，所以坏的测试比不测更糟（p.295–296）。作者也说协议没有对错，是在给定资源下尽量拿到有用知识的手艺（p.296）。

四个分支：分支 1 把一次试玩的协议写全；它的「测试者」一栏由分支 3 填，「停测条件」一栏由分支 4 填；写完或拿到别人的协议，用分支 2 逐条查失效。试玩现场怎么主持、测后怎么问，在 `sylvester-playtest-observation.md`。

术语：Kleenex 测试者，从没玩过这款游戏的人，只能用一次；WYSIATI（what you see is all there is），以为看到的就是全部。

## A1 — 书中案例 (Past Application)

- **分支 2｜失败的多人射击（转述，p.296）**：作者访谈过一位资深设计师，他们的协议是一群人坐在一个有吃的房间里长时间一起玩。游戏显得很好，团队据此迭代打磨到又深又平衡；但协调良好、沟通充分的队伍里它闪光，到了网上，太依赖精细团队战术，陌生人玩不转就崩了，游戏在市场和多数玩家那里失败。
- **分支 3｜作者用同事测战斗（作者亲历，p.298）**：同事了解这款游戏，但没见过他正在做的那场战斗，起始知识近似玩了几小时后才遇到这场战斗的真实玩家。
- **分支 1、4｜原书未提供完整案例，以下是合成演练**：一款带程序生成地图的生存游戏，前 3 场试玩经历都很不同，团队想据此砍掉夜晚系统。按分支 4 归入无约束的系统驱动一档，前 3 场没有重复，不据此砍系统，继续测到开始常常重复再定；协议的「测试者」栏按分支 3 混入没玩过的人和老玩家。

## A2 — 触发场景 (Future Trigger) ★

**情境**

1. 准备一次试玩，要写测试计划或协议。
2. 内部测试一直很顺，外部玩家或上线后的反馈却很差。
3. 招测试者：找新人还是老玩家，找高手还是普通玩家。
4. 测了一两场就想改设计；不知道测几场才够、什么时候能停。
5. 评审别人的测试方案，看有没有会污染结论的地方。

**语言信号**

- 测试方案怎么写 ／ 试玩协议 ／ 找谁来测 ／ 测几场才够 ／ 什么时候可以停测 ／ 内部测着挺好上线就崩 ／ 就凭这两场能不能改
- playtest plan ／ test protocol ／ Kleenex testers ／ how many playtests ／ playtest sample size ／ when to stop playtesting ／ biased playtest

**与相邻卡的区分（初稿）**

- 试玩现场怎么观察、自测何时切旁观、怎么主持、测后怎么问、建议怎么用 → `sylvester-playtest-observation.md`
- 埋点、数据、大样本找稀有情况 → `sylvester-metrics-and-telemetry.md`
- 该做哪种测试、这个问题该不该靠测试解决 → `sylvester-knowledge-creation-method.md`
- 迭代环怎么定 → `sylvester-iteration-loop.md`；平衡改不改、怎么改 → `sylvester-balance-change-review.md`

## E — 执行 (Execution)

### 先选分支

| 你的问题像…… | 走 |
|---|---|
| 要为一次试玩写协议 | 分支 1 |
| 已有协议或测试结论，要查有没有污染 | 分支 2 |
| 这次找谁来测 | 分支 3 |
| 测几场够、什么时候停、能不能凭这几场改设计 | 分支 4 |
| 现场怎么看、怎么主持、测后怎么问 | `sylvester-playtest-observation.md` |

### 分支 1：试玩协议模板

- **输入**：要测的版本和段落；可用的人、时间、场地。
- **步骤**：
  1. 写本次要回答的设计问题：玩家哪里困惑、哪里太易或太难、平不平衡、有没有退化策略、看不看得懂叙事；试玩不是为了找技术问题或收集市场数据（p.295）。完成标准：问题清单里没有 bug 和市场项。
  2. 选测试方式：自测最便宜，最早几轮用；旁观测试换不具备设计者知识的人来玩（p.296–297）。自动数据和专门实验室作者只提了一句（p.287），本卡不展开。完成标准：写明方式和理由。
  3. 选测试者，转分支 3。
  4. 写执行规则：几乎所有情况下设计者全程沉默，被问就中性地拒答（p.297）。主持细节见 `sylvester-playtest-observation.md` 分支 2。完成标准：规则写进协议。
  5. 事先写好必须补给玩家的信息，用来填补游戏还缺的部分（p.297）。完成标准：补充信息逐条写出，测试中不临时加。
  6. 写测后提问（问法见 `sylvester-playtest-observation.md` 分支 3）和停测条件（转分支 4）（p.299–300）。
  7. 写完过一遍分支 2。
- **判停 / 转向**：资源有限时选哪种方式、测多少人、接受哪些已知缺陷，原书没有对错（p.296），由设计者定并写明理由。
- **输出**（约定）：协议文档「设计问题 / 测试方式 / 测试者 / 执行规则 / 预写补充信息 / 测后提问 / 停测条件」，每栏附理由。

### 分支 2：协议失效审查

- **输入**：现有协议：谁测、在哪测、和谁一起、能不能交流、设计者事先说了什么；真实玩家会在哪里、和谁一起玩。
- **步骤**：
  1. 对照测试情境与真实游玩情境，写出协议会藏住哪些设计失败；作者的案例是朋友同屋长时间一起玩，对比陌生人在网上玩（p.296）。完成标准：每处差异写出可能藏住什么。
  2. 逐条查五类失效（p.296）：
     - 未盲测 → 测试者有期望偏差（「盲测」具体怎么做原书没解释）
     - 群体测试 → 社会竞争和跟风意见
     - 让玩家出声思考 → 便于解读，但改变了他的行为
     - 测试者选择 → 藏住只在特定年龄、性别、文化、技能水平的人玩时才出现的问题
     - 测试者太少 → 随机波动大得出人意料

     完成标准：每类标「存在 / 不存在 / 不适用」并写证据。
  3. 再查旁观测试最大的风险：给了玩家真实玩家不会有的信息（p.297）。完成标准：标出协议里设计者可能开口的每个环节。
  4. 列出存在的风险和它可能掩盖的设计失败。缓解只写原书给过的：沉默规则（p.297）、测试者混合得像目标玩家（p.298）、多测几场（p.298–299）；其余类型原书未给缓解办法，能接受多少由设计者定。
- **判停 / 转向**：作者说这些失效永远无法完全避免（p.296）。坏协议没有反馈，审查本身也无法验证。
- **输出**（约定）：风险表「失效类型 / 是否存在 / 证据 / 可能藏住的设计失败 / 原书给的缓解」。

### 分支 3：按测试目的选测试者

- **输入**：这次要拿什么数据；目标玩家是谁。
- **步骤**：
  1. 写清这次要拿的数据：测试者主要差在对游戏的了解程度，这决定你拿到什么数据（p.297）。
  2. 按数据选人（p.297–298）：
     - 玩家开头几分钟的反应 → 从没玩过的 Kleenex 测试者，每人只能用一次
     - 高技能平衡 → 能长时间高强度玩的人，通常是每天练技术的专职测试团队
     - 玩到中途才遇到这一段的感受 → 了解游戏但没见过这一段的人

     完成标准：每个测试目的对应一类测试者。
  3. 再按年龄、文化、社会经济背景、兴趣等维度混合，使整组像你希望玩到成品的人（p.298）。完成标准：写出目标玩家画像，并和这组人对照。
- **判停 / 转向**：其他目的（如叙事理解）和混合比例原书未说明，交设计者。
- **输出**（约定）：招募表「测试目的 / 测试者类型 / 每人可用次数 / 与目标玩家的对照」。

### 分支 4：场次与停测

- **输入**：游戏能生成的体验有多宽；已测各场的记录。
- **步骤**：
  1. 不把一两场当成整个游戏：大脑会以为看到的就是全部，只见过一两条路径时，解决看到的问题会在没看到的体验里制造新问题，游戏一直在变却不变好（p.298）。完成标准：写明当前判断基于几场。
  2. 按体验广度预估场次（p.299）：没有统一的数字；作者的经验估计是很简单、受限的游戏两三场，射击战斗六到十二场，无约束、系统驱动的游戏可能非常多。完成标准：写明归入哪一档。
  3. 每场记下这位测试者走过的体验路径（p.298–299）。完成标准：每场一条记录。
  4. 开始常常看到测试者重复同样的体验时停测（p.299）。「同样的体验」「常常」怎么算原书未说明，由设计者判断；记重复次数是约定。完成标准：重复计数和停或续的决定。
- **判停 / 转向**：本分支不承诺「一两场后不许改」：作者自己的战斗流程每测一场就改明显的问题（p.286），它和本节警告之间怎么协调，原书未说明。第 6 章另有一处场次说法，与本分支不一致，该单元待核查，只列在 B 段对照，不作本分支的依据。
- **输出**（约定）：场次记录「场次 / 测试者 / 体验路径 / 与前几场重复的体验」，加停测判断。

## B — 边界 (Boundary)

**不要用这张卡**

- 现场观察、主持和测后提问 → `sylvester-playtest-observation.md`；靠数据找稀有情况 → `sylvester-metrics-and-telemetry.md`。
- 把一份字段齐全的协议当成协议有效的证明：原书没有检验协议的办法（p.295）。

**作者警告的失败模式**

- 坏的测试比没测更糟：它给设计者的是不真实的知识（p.295–296）。预警：测试者彼此认识、坐在一起、能语音沟通，真实玩家却不会；测试结果一直很好，和外部反馈差距大。
- 盯住一次试玩的结果改设计（p.298）。预警：改动理由是「昨天那个测试者」；每轮只有一两个测试者。

**作者盲点与时代局限**

- 测试资源的例子默认中大型工作室，有专职测试团队；数据手段几乎全靠人工试玩（编者评注，非原书）。
- 「只有发售给真实玩家才拿到真正的反馈」（p.309）的前提早于抢先体验和直播（编者评注，非原书）。

**各分支的已知缺口**

- 分支 1：协议是否有效无法事先检验；作者说这些失效无法完全避免（p.296）。
- 分支 2：情境不一致只有一个失败案例（多人射击）；「未盲测」的含义原书没解释；情境不一致、未盲测、群体测试、出声思考四类没给缓解办法。
- 分支 3：默认有专职测试团队和足够的测试者；Kleenex 测试者消耗快，小团队怎么办原书未说明；测试者选择本身也会引入偏差（p.296）。
- 分支 4：两三场、六到十二场都是作者的经验估计；第 6 章的 10–20 场（p.173）与第 11 章的分档（p.299）不一致，原书没有统一；停测法则对很少出现的体验可能不敏感，这是复核者的判断，原书未讨论；与作者战斗例子的张力见分支 4。

**对照：第 6 章的场次说法（依据不足）**

- 第 6 章（p.173）：一场是一个故事，三场是三个故事；10、15 或 20 场之后，理解开始从故事转向系统（作者的经验估计）；要尽量多测，找尽量不同的玩家。
- 依据不足的原因：第 6 章判断测够的依据只是「开始按系统而非故事思考」这一自我感受，无法检查；场次又与第 11 章 p.299 的分档和「没有统一数字」不一致。所以它不进分支 4 的步骤，只在这里并列，不替作者选。
