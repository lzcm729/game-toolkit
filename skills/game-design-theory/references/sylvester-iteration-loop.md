# 迭代循环设计

> **怎么用这张卡**：它是方法和书中依据的来源之一，不是回答的模板。回答围绕用户的处境：先给你自己的专业判断和具体做法，书外的实操（算一个例子、查数据、估成本）照常给；再用这张卡补方法、校正判断。不要按卡的分段复述这本书；卡里没写的，不等于不能答。书名和页码只在用户要出处时给。

## R — 原文 (Reading)

> ITERATION is the practice of making short-range plans, implementing them, testing them, and repeating.
>
> 译：迭代，就是做短程计划、实现它、测试它，然后重复。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / Iteration, p.283

> It exchanges deep planning for reality checks. It tests the broad structure before investing in detail polish.
>
> 译：它用现实检验换掉深度计划。它先测大结构，再在细节打磨上投入。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / Iteration Example, p.287

> The FALLACY OF VISION is the idea that a mental movie of an experience is equivalent to a design for a system that generates that experience. … instead of trying to envision the best experiences generated by a game, try to envision the worst.
>
> 译：愿景谬误，是以为一段体验的脑内电影就等于生成这段体验的系统设计。……别去设想游戏能生成的最好体验，去设想最糟的。
>
> — Tynan Sylvester, *Designing Games*, Ch11 Planning and Iteration / The Fallacy of Vision, p.305

## I — 方法骨架 (Interpretation)

这张卡回答「一轮迭代怎么定、一段内容怎么一轮轮做出来、一个愿景背后的系统会生成什么」。作者的前提是游戏设计的计划不确定性很大，纸面上读不出设计能否成立，所以只计划到本轮测试为止，用测试校验假设，再据观察定下一轮。迭代（iteration）就是这个环；愿景谬误（fallacy of vision）是把脑中一段精彩体验当成了生成它的系统。

分支 1 通用，给任何设计挑战定环或评审流程；分支 2 是作者唯一完整的例子，只适用于机制驱动的战斗或关卡段落；分支 3 用在提案只是一段体验描述时，补出被想象剪掉的最糟体验，它只能质疑愿景，要知道真实会怎样还得回分支 1 做出可测版本。

作者观点（参考单元）：早期暂时接受粗糙的工作，最终质量反而更好（p.303–304）；试玩中的意外发现常最有价值，要留心捕捉（p.306–308）。

## A1 — 书中案例 (Past Application)

- **分支 1、2｜作者的射击战斗流程（作者亲历，p.284–287）**：一小时粗搭出的第一版很烂，常忘了给玩家武器，但环闭合了；灰块里试过塔楼、桥、雷区、战壕、炮击；旁观的同事有人远程狙光、有人冲过敌线、有人掉进没看到的洞。作者自述结果：交给真实玩家前已知道它怎么玩。
- **分支 3｜年轻航空工程师（例题，p.304–305）**：新人向老板描述一次完美航班，五分钟登机、包厢里喝马提尼；老板说「你被解雇了」：他描述的是一次飞行，不是一架飞机。

## A2 — 触发场景 (Future Trigger) ★

**情境**

1. 要给关卡、系统、工具或界面安排节奏：一轮做到哪、怎么测、何时停。
2. 团队流程是先写完全部规格或做完全部美术再试玩。
3. 要从零做一场战斗遭遇或一个关卡段落，想要分阶段的做法。
4. 提案是一段精彩的玩家故事或概念视频，没有机制描述。

**语言信号**

- 一轮迭代怎么定 ／ 先做完再测还是边做边测 ／ 这场战斗怎么一步步做出来 ／ 这个愿景听着很好，玩起来会怎样 ／ 最糟会是什么体验
- iteration loop ／ iterative process ／ build-test cycle ／ fallacy of vision ／ worst-case experience ／ the pitch only shows the best moments

## E — 执行 (Execution)

### 先选分支

| 你的问题像…… | 走 |

| 给一个设计挑战定迭代环，或评审团队现有流程 | 分支 1 |

### 分支 1：迭代环的定义与流程评审（u11-03）

- **输入**：设计挑战是什么；要评审时，团队现在怎么做；可用的测试方式。对象说不清先问。
- **步骤**：
  1. 定迭代对象：整款游戏、一个关卡、一个工具或一个界面；大团队应同时跑多个环（p.284）。完成标准：写明对象，多个环逐个列出。
  2. 本轮计划只写到本环结束，不必预测更远（p.283）。完成标准：计划里没有本轮测试之后的条目。
  3. 尽快做出能测的版本，粗糙也行，作用是让环闭合、让设计从脑内电影变成实物（p.284）。完成标准：写明可测版本。
  4. 测试，用现实校验假设；方式有自测、旁观、自动数据、专门实验室（p.283、p.287）。完成标准：写明方式；协议转 `sylvester-playtest-protocol.md`。
  5. 下一轮的改动只回应测试中真实观察到的问题，不回应想象的问题（p.285）。完成标准：每条改动能指回一次观察。
  6. 定停止条件，原书给三种：预定轮数、达到目标质量、钱用完（p.284）。「目标质量」怎么判原书未说明，选它就由设计者写出门槛。完成标准：选定一种并写明门槛。
  7. 评审流程时对照三条原则（p.287）：用现实检验换掉深度计划；先测大结构，再投入细节打磨；不对远期计划投入过深，随不可预测的测试结果持续调整。完成标准：每条写「符合 / 违反」和证据。
- **判停 / 转向**：环多长转 `sylvester-process-and-planning-horizon.md`，作者的方向性判断是计划越不确定、视距越短（p.288）。每个挑战的流程都要定制（p.284），分支 2 只是机制驱动内容的一个模板。
- **输出**（约定）：环定义表「对象 / 本轮做到什么 / 可测版本 / 测试方式 / 改动来源 / 停止条件」；流程评审表「原则 / 符合或违反 / 证据」。

### 分支 2：机制驱动战斗场景的分阶段迭代（u11-04）

- **输入**：要做的内容，确认它是机制驱动的（以平衡和节奏为先的战斗遭遇、关卡段落），否则停，见 B 段；有没有关卡美术；能否找到没见过这一段的测试者。
- **步骤**（时长和轮数都是作者做射击战斗的经验估计；阶段切换只有作者的定性描述，由设计者判断）：
  1. 粗搭：想到什么放什么，不停下分析，唯一目标是尽快能玩；作者用一小时内（p.284）。完成标准：能从头玩到尾。
  2. 概念轮：灰块里做大的概念跳跃，如塔换成桥、换掉主要威胁，几分钟一试，不管细节；作者说三到八轮后落到一个行得通的概念（p.285）。完成标准：记下试过的和选定的概念。
  3. 细化轮：环拉长到两三小时一测，改动缩小到墙和柱子的位置，只改测试里真实看到的问题；请关卡美术做可行性咨询，他还不直接做空间（p.285）。完成标准：每条改动对应一次观察。
  4. 旁观测试轮：自测不再教你新东西时，换没见过这场战斗的人玩，什么都不说、站在视线外；每场列问题，半天改完，换新人再测，作者转了 10 到 20 轮、两三周，直到节奏和平衡良好、能应付多种技能水平和习惯（p.285–286）。主持规则见 `sylvester-playtest-observation.md` 分支 2。
  5. 美术轮：灰块换成真资产，再测美术怎样改变玩家对战斗的感知；出问题时设计改脚本细节，或美术补光、简化以减少美术噪声；环长到几天，几轮后机制和美术都成立（p.286–287）。完成标准：美术前后的试玩问题各有记录。
  6. 多学科轮与 QA：换真对白、过一遍音效、用空间表达世界叙事、编剧重写对白；测试员找技术 bug，修完发布（p.287）。完成标准：每项有负责人。
- **判停 / 转向**：作者声明这个流程不适合别的挑战或开发者，只是一例（p.284）。上美术的时机和复测转 `sylvester-graybox-and-art-timing.md`。
- **输出**（约定）：阶段计划表「阶段 / 作者的循环长度与轮数（经验估计）/ 改动对象 / 测试方式 / 进入下一阶段的信号」。

### 分支 3：愿景谬误与最糟体验反演（u11-21）

- **输入**：愿景或提案的原文；系统大致的机制。只有体验描述、没有机制，这一点本身先记下来。
- **步骤**：
  1. 写下愿景描述的最佳体验（p.305）（约定）。完成标准：一段话。
  2. 标出愿景没说的：系统背后的取舍和代价，同一系统还会生成的其他体验；玩家体验的是全部，不只是最好的部分（p.305）。完成标准：两栏都有内容。
  3. 逐一仔细想象最糟的体验：令人沮丧的失败、无聊的重复、不清楚的交互（p.305）。完成标准：三类各有条目，想不出的写明。
  4. 补上被剪掉的平常时段：精彩战斗之外从基地走过去的五分钟，关键一救之外的十次随机失败（p.305）。完成标准：列出平常时段。
  5. 最佳与最糟并列，得到平衡的图景，用它质疑愿景的准确度（p.305）。改不改设计原书未说明，交设计者。
- **判停 / 转向**：作者不反对愿景，它能激励人（p.305）。清单仍是想象，不能代替试玩：没人能在脑中把机制和玩家选择模拟成事件（p.303）；转分支 1 做出可测版本。
- **输出**（约定）：并列表「愿景里的最佳体验 / 三类最糟体验 / 被剪掉的平常时段 / 愿景没说的机制与取舍」。

## B — 边界 (Boundary)

**不要用这张卡**

- 定环长和规划视距 → `sylvester-process-and-planning-horizon.md`。
- 把分支 2 外推到叙事驱动、角色、界面、系统设计：作者只说这些各需不同的方法，没给示例（p.287）。

**作者警告的失败模式**

- 按想象的问题改设计（p.285）。
- 早期每轮都追求质量、过度分析，轮数变少，最后反而更差（p.303–304）。
- 愿景只想到最好的体验，藏住缺陷、制造过度自信和过度规划（p.305）。预警：提案是一段玩家故事，没人讨论最无聊、最挫败的时刻。

**作者自留的张力**

- 第 12 章作者自称三步迭代环是 criminal oversimplification，前面的迭代图是错的，真实过程更有机（p.321）。
- 迭代只优化、不带来革命；何时停下小步测试、做未经测试的大跳跃，作者没给判据（p.289–290，该单元待核查）。
- 质量悖论里「迭代轮数是游戏质量最重要的单一决定因素」（p.304）未经系统验证（批判节）。

**作者盲点与时代局限**

- 原图缺失（转换时丢失）：线性流程图和迭代环图都丢了，环的结构按正文重建（计划 → 实现 → 测试 → 重复）。
- 测试资源默认中大型团队（批判节）。

**各分支的已知缺口**

- 分支 1：「目标质量」怎么判原书未说明；停止条件之一是钱用完，不是设计判据。
- 分支 2：只有这一个完整案例；所有时长与轮数都是作者射击战斗的经验估计；用同事旁观是退而求其次，理想是从目标市场随机抽的真实玩家（p.286），小团队怎么找测试者原书未说明。
- 分支 3：原书只给三类方向，没有穷举方法；清单出来后怎么权衡原书未说明。
