# 操控与手感

> **怎么用这张卡**：它是方法和书中依据的来源之一，不是回答的模板。回答围绕用户的处境：先给你自己的专业判断和具体做法，书外的实操（算一个例子、查数据、估成本）照常给；再用这张卡补方法、校正判断。不要按卡的分段复述这本书；卡里没写的，不等于不能答。书名和页码只在用户要出处时给。

## R — 原文 (Reading)

> The goal of input design is to achieve synchronization between a player’s intent and in-game action.
>
> 译：输入设计的目标，是让玩家的意图与游戏内的动作同步。
>
> — Tynan Sylvester, *Designing Games*, Ch9 Interface / Input, p.235

> A game must map exclusive controls to actions that are exclusive in the game.
>
> 译：游戏必须把互斥的控件，映射到在游戏里也互斥的动作上。
>
> — Tynan Sylvester, *Designing Games*, Ch9 Interface / Control Arrangement, p.237

> But these methods are the exception to the principle of elegance. They cost us a great amount to design, but they cost the player nothing because he never senses they’re there.
>
> 译：但这些方法是优雅原则的例外。它们让我们付出很大的设计成本，却不让玩家付出任何代价，因为他从来感觉不到它们的存在。
>
> — Tynan Sylvester, *Designing Games*, Ch9 Interface / Control Feel, p.239

## I — 方法骨架 (Interpretation)

这张卡回答「按键怎么排、操作为什么不跟手、要不要做辅助、帧率选多少」。四个分支各管输入链上的一段：

- 分支 1：映射（mapping，控件与游戏内效果之间的相似）和控件互斥（control exclusivity，哪些控件因为手与设备的物理关系不能同时用），排键位时在纸面上查；
- 分支 2：手感（control feel，每一刻把意图投射进游戏的体验）的微规则，这些规则是「笨」的，不猜玩家想干什么；
- 分支 3：输入辅助（input assistance，对原始输入的预处理），猜玩家的意图并悄悄修正输入；
- 分支 4：操控延迟（control latency，本机从收到输入到显示可感知反馈的时间，不是网络延迟）与帧率取舍，是立项、定性能预算时的决定。

手感不对先看分支 2，需要猜意图再到分支 3。分支 2、3 加的隐藏复杂度，作者明说是优雅原则的例外。

作者观点（参考单元）：输入越好越看不见，玩家会把功劳记在画面或平衡上，资源紧时它最先被砍；作者认为几乎总值得投入（p.245）。

## A1 — 书中案例 (Past Application)

- **分支 1｜BioShock（转述，p.236–237）**：左手法术、右手武器分别用左右扳机，对应玩家的双手；血量指示是红的，回血键也是红的。手柄每个食指旁的肩键和扳机不能同时按，BioShock 用肩键选武器、扳机开火，正对应「换武器时不能开火」，还顺带教会了这条限制。反例：十字键选工具、左摇杆移动，都归左拇指，换工具就得停下。灶台映射图在转换中丢失，正文只说旋钮与炉眼在空间上对应。原书未说明结果。
- **分支 2｜Mario 的跳（转述，p.238–239）**：按键时长决定跳多高；上升时重力很小，过顶点后变为三倍，下落有终端速度；助跑跳得更高；空中能控制水平移动但不如地面；落地前几帧按跳，着地瞬间自动起跳。作者把 Mario 的成功归于操控本身就是乐趣（作者判断）。
- **分支 3｜Halo（转述，p.240–241）**：瞄准辅助拆成跟踪移动目标、松杆减速时把准星滑到附近目标、快要扫过目标时微调方向等子系统，强度随距离、角距、其他目标、难度、武器而变；狙击枪不开镜时零辅助，近距离用法多了一层隐藏难度，玩家更愿意按设计意图用它，没人察觉（作者描述）。
- **分支 4｜183 ms（例题，p.243）**：30 fps、四帧延迟、电视再加 50 ms，总延迟 183 ms；看到准星压住目标才开枪会打空，玩家得学会提前几帧扣扳机。

## A2 — 触发场景 (Future Trigger) ★

**情境**

1. 排手柄、键鼠或触屏的键位。
2. 试玩者说操作别扭、发黏、按了没反应，或为了换工具得停下。
3. 手柄或触屏上瞄准、近战、跳跃落点不准，考虑做辅助。
4. 立项或定性能预算时要在 30 和 60 fps 之间选。
5. 手感打磨在排期里要被砍。

**语言信号**

- 按键怎么布局 ／ 操作不跟手 ／ 手感差、发软 ／ 按了没反应 ／ 要不要做辅助瞄准 ／ 30 还是 60 帧 ／ 输入延迟多少
- control mapping ／ button layout ／ game feel ／ controls feel mushy ／ input buffering ／ dead zone ／ aim assist ／ input lag ／ 30 vs 60 fps

**与相邻卡的区分（初稿）**

- 某个武器或单位太强、整体怎么削（辅助只是其中一根杠杆）→ `sylvester-balance-change-review.md`
- HUD 反馈不显眼 → `sylvester-signal-visibility.md`
- 网络延迟、联机同步：原书未涉及，不是这张卡

## E — 执行 (Execution)

### 先选分支

| 你的问题像…… | 走 |
|---|---|
| 排键位，或玩家为做一件事得停下另一件 | 分支 1 |
| 操作发软、按了没反应、技能上限太低 | 分支 2 |
| 设备精度不够，要猜玩家想打谁、想落哪 | 分支 3 |
| 定帧率、估输入延迟 | 分支 4 |

### 分支 1：映射与控件互斥（u09-12）

- **输入**：游戏内动作清单；输入设备；哪些动作在游戏里需要同时做。同时性不清先问。
- **步骤**：
  1. 为每个动作找一个在位置、形状、颜色、运动等方面与其效果相似的控件（p.236）。相似性是自带的记忆提示，能减学习负担，对经验少的玩家尤其重要（p.236–237）。完成标准：映射表，每行写相似性依据，找不到的标出。
  2. 标出物理上不能同时用的控件组，如只有同一根手指够得着的两个键，体感设备上一只手臂不能同时发两个信号（p.237）。完成标准：互斥组清单。
  3. 对每个互斥组查：映射到的动作在游戏里是否也互斥（p.237）。完成标准：冲突清单。
  4. 每个冲突列出作者给的两种修法：换一个控件，或在游戏里加一条与物理限制对应的限制（p.237）。选哪种原书没给判据，交给设计者；映射和互斥两条原则互相冲突时怎么取舍，原文也没说。完成标准：每个冲突有两种修法候选。
- **输出**（约定）：映射表「动作 / 控件 / 相似性依据」，冲突表「互斥组 / 动作 / 修法候选 / 设计者的选择」。

### 分支 2：手感微规则（u09-13）

- **输入**：核心操作（如跳）；现有规则；试玩里的症状。
- **步骤**：
  1. 把这个操作拆成规则：按键时长、重力、速度上限、助跑加成、空中控制、提前输入等（Mario 例，p.238）。完成标准：规则清单。
  2. 给每条写目的。作者举的两类：抬高技能上限（助跑跳得更高），消除按了没结果的微小挫败（落地前的按键会被记住）（p.238–239）。这两类是例子，不是穷尽分类，别的目的照实写。完成标准：每条有具体目的。
  3. 对照跨类型手段（p.239）：给控件小死区，或在几帧内平滑，去掉噪声输入；提前到达的输入记住片刻，执行前又检测到别的按键就丢弃；组合键与单键按不同方式解释；推到底时进入超出常规范围的加速模式。完成标准：每项写明已有 / 不需要 / 要加。
  4. 评审时不要把这些规则当冗余砍：它们开发成本高，但玩家感觉不到，是优雅原则的例外（p.239）。完成标准：评审意见里没有以「规则太多」为由删手感规则。
- **判停 / 转向**：本分支只交规则清单和目的标注。原文除 Mario 的重力三倍外没给参数，也没有调试流程；数值交给设计者试手感，作者说手感好坏要练出来才分得清（p.245）。需要猜玩家意图时转分支 3。
- **输出**（约定）：表，列为「规则 / 目的 / 状态 / 待调参数」。

### 分支 3：输入辅助（u09-14）

- **输入**：要辅助的操作（瞄准、跳跃落点、攻击、驾驶、移动，p.241）；输入设备；玩家想达成什么；是否用于多人对战。
- **步骤**：
  1. 写出要猜的意图（例：想让准星停在目标上）（p.239）。完成标准：一句意图。
  2. 拆成几个交错的子系统，不做一个直接把准星拉向目标的辅助，那样太明显（p.240）。完成标准：子系统清单，各写作用。
  3. 逐个写为什么玩家察觉不到：只作用于玩家天然测不出的量，如早停几像素、略快加速、只调方向不调速度，被周围的运动掩盖（p.240）。完成标准：每个子系统写出掩盖它的运动；写不出就重做。
  4. 列出强度随哪些因素变：目标距离、与准星的角距、有无其他目标、难度、所用武器等（p.240）。完成标准：每个子系统的因子清单。强度多大、玩家实际会不会察觉，原书没给测试方法和数值，交给试玩。
  5. 需要时当隐形的平衡杠杆：对不希望的用法给零辅助（狙击枪不开镜，p.241）。完成标准：写明压的是哪种用法。
- **判停 / 转向**：本分支只交子系统清单。多人对战里隐形辅助的公平与知情作者没讨论，由设计者另行判断。
- **输出**（约定）：表，列为「子系统 / 作用 / 触发条件 / 为什么察觉不到 / 强度因子」。

### 分支 4：延迟估算与帧率取舍（u09-15）

- **输入**：候选帧率；管线延迟帧数（由程序确认：没有额外延迟时 3–4 帧，硬件上不可能低于 3 帧，代码写得差会到 5、6、7 帧甚至更多，p.242）；显示设备延迟（ms）；预期玩家技能；操控方式；游戏主要的情绪触发器。显示延迟不知道就单列「+ 屏幕延迟」，不猜数。
- **步骤**：
  1. 算：总延迟 = 延迟帧数 × (1000 ÷ 帧率) ms + 屏幕延迟（p.242–244）。30 fps 为 100–133 ms，60 fps 为 50–67 ms，各加屏幕延迟（p.244）；作者算例 4 × 33.3 + 50 ≈ 183 ms（p.243）。取整到 1 ms（约定）。完成标准：每个候选帧率一个区间。
  2. 不拿电影、电视帧率或人的反应时当标准：要看的是输入到反馈的延迟，它是帧间隔的三到四倍；问题是游戏回应玩家够不够快（p.243）。延迟越长，玩家越要提前预判，越需要技能、越不同步（p.243）。完成标准：决策依据写的是延迟。
  3. 按预期技能、操控方式、情绪触发器选（p.244）：靠美术或叙事的，或靠技能但不需要快速输入的（回合制策略），常用 30；高技能玩家操作要求快速响应的系统时，60 不可少，射击、竞速、格斗最常见。多高的技能算高没有阈值，由设计者判断。完成标准：选择及对应判据。
  4. 选 60 就备好游说要点：每帧可用算力约为 30 fps 的三分之一（Carmack，p.244）；美术要规模和细节，程序要 AI 和物理的算力，市场要截图，代价落在各方身上而好处难见，所以天然有反对 60 的政治偏向（p.244–245）。完成标准：每方的代价和对应的收益论据。
- **判停 / 转向**：本分支只承诺作者的四级管线模型（输入、逻辑、渲染、显示，p.241–242）和 30/60 二选一的判据。候选帧率不是 30 或 60，或问到高刷新率、可变刷新、触屏输入延迟：公式照算，选择判据不套，标「原书范围外」。p.242 说 3–4 帧，p.244 写「最优四帧」却给出 3–4 帧的数值，这里取 3–4 帧。
- **输出**（约定）：表，列为「帧率 / 延迟帧数 / 帧时长 / 屏幕延迟 / 总延迟 / 判据 / 选择 / 游说要点」。

## B — 边界 (Boundary)

**不要用这张卡**

- 网络延迟、联机预测：本章讲的是本机管线延迟。
- 外设本身的物理手感、人体工学：作者说的 control feel 不指这个。
- 武器整体平衡 → `sylvester-balance-change-review.md`。

**作者警告的失败模式**

- 操作迟钝、不直观，挫败感包住整个体验，盖住好游戏（p.235）。
- 互斥控件映射到可以同时做的动作（p.237）。
- 以简洁、优雅为由砍手感规则（p.239）。
- 照搬影视帧率或拿反应时定帧率（p.243）；该用 60 的游戏在各方压力下退回 30（p.244）。
- 输入因为看不见而被砍（p.245）。

**作者盲点与时代局限**

- 隐形辅助按「玩家察觉不到」当优点讲，知情与公平没讨论（批判节：隐形设计的伦理）。
- 30/60 二选一和电视延迟是 2012 年前后的硬件前提，可变刷新率、高刷新率显示器不在书里；「60 以上很少有人感觉得到」只有经验依据（批判节）。
- 映射与互斥只讨论手柄和体感，按一般玩家的身体讲，身体障碍玩家的需求不在讨论内（批判节：accessibility 不涉及身体障碍）。
- 隐形辅助的知情与公平作者没讨论（p.240）；详述案例只有 Halo 的瞄准辅助。手感微规则的详述案例只有 Mario。
- 「每帧算力约为 30 fps 的三分之一」是转引 Carmack 的数字（p.244）。

**原图缺失（转换时丢失）**

- 灶台映射图（p.236）：正文已讲清旋钮与炉眼的空间对应，不影响分支 1。
- 渲染管线图（p.242）：正文已逐帧写清四个阶段，不影响分支 4 的计算。

**各分支的已知缺口**

- 分支 1：换控件还是加规则没有判据；两条原则冲突时的取舍未说明。
- 分支 2：没有参数，也没有调试流程；两类目的不是穷尽分类。
- 分支 3：没有参数和察觉测试方法，多人对战的公平未讨论。
- 分支 4：「高技能」没有阈值；高刷新率、可变刷新、触屏延迟不在原文范围。
