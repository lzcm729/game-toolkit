# 依赖栈与开发顺序

> **怎么用这张卡**：它是方法和书中依据的来源之一，不是回答的模板。回答围绕用户的处境：先给你自己的专业判断和具体做法，书外的实操（算一个例子、查数据、估成本）照常给；再用这张卡补方法、校正判断。不要按卡的分段复述这本书；卡里没写的，不等于不能答。书名和页码只在用户要出处时给。

## R — 原文 (Reading)

> A DEPENDENCY is a relationship between two parts of the design such that changes in one part would force changes in the other.
>
> 译：依赖是设计中两部分之间的一种关系：一部分改了，会迫使另一部分跟着改。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies, p.323

> The dependency stack deliberately ignores the weakest dependencies so that we can focus on the most important and potentially dangerous ones.
>
> 译：依赖栈有意忽略最弱的依赖，好让我们盯住最重要、可能最危险的那些。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies / The Dependency Stack, p.327

> Uncertainty multiplies through dependencies. … Start at the bottom of the dependency stack, and work upward through each iteration loop.
>
> 译：不确定性沿着依赖相乘。……从依赖栈底部开始，每一轮迭代往上推一层。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies / Cascading Uncertainty, p.328–329

## I — 方法骨架 (Interpretation)

这张卡回答「先做什么、什么现在不该做」。依赖的判据是「A 的设计改了会不会迫使 B 改」，不是「A 会不会影响 B」（p.323, p.326）。依赖栈把设计拆成元素、只留关键依赖、画成栈，底层不依赖任何东西（p.324）。确定性是设计者估计的、一个元素不经大改就照写成立的概率；上层元素原样存活要靠自己和下面每一层都不出问题，所以概率相乘、越往上越低，上层几乎总要大改（p.328–329）。结论是从栈底做起，底层稳了再往上加。

分支 1 判一对元素、决定内容先不先做，是其他分支的基本动作。整款游戏按分支 2 画栈 → 分支 3 算存活概率 → 分支 4 排迭代顺序。分支 5 是同一套做法用在单个系统或角色上，作者说日常多半这样用（p.334）。低概率的上层怎么存放、核心怎么找，见 `sylvester-core-and-backlog.md`。

作者观点：高度衍生、基于成熟设计的游戏，每个元素都很确定，几乎可以按任意顺序做（p.328）。

## A1 — 书中案例 (Past Application)

以下都是作者虚构的例题，原书未说明实际结果。

- **分支 1｜5 km/h 的动画（p.324）**：给每个方向 5 km/h 奔跑的角色做完全套动画，后来改成 7 km/h，动画全部重做；先在灰盒里定移动再做动画就不会浪费。
- **分支 2｜Fantasy Castle（p.324–328）**：22 个子系统各有几页纸面设计。正文写出的主链：陷阱和加固依赖哥布林袭击，袭击依赖战斗，战斗依赖城墙和角色，城墙依赖建造，建造依赖角色。城墙和建造互相影响，建造改了几乎必然改城墙，反过来只在某些情况下，栈里保留前一个方向。栈图原图缺失（转换时丢失），其余元素的位置不能复原。
- **分支 3｜哥布林袭击（p.328–329）**：自身确定性 80%，加上下层，0.8 乘五次约 33%；若每个系统只有 30%，五层之上原样存活约 0.2%。
- **分支 4｜Fantasy Castle 往上长（p.330–332）**：先只做角色、建造、城墙，迭代好了加农耕，再加贸易和季节；试玩农耕后可能觉得季节没必要、作物病害更有意思，栈顶随之重组。农耕纸面 60%，实现并试玩后到 90% 以上。原文前后不一致：p.330 起步三项含城墙，p.331–332 的核心是角色、建造、农耕。
- **分支 5｜角色 Capp（p.334–336）**：六项能力。倒地依赖旋踢，扫腿闪避依赖倒地，蹬墙跳延伸自速度，手翻踢是蹬墙跳的攻击版。核心是旋踢加速度，撑起「速度型」定位。栈图和核心图原图缺失（转换时丢失），依赖关系正文写全了。

## A2 — 触发场景 (Future Trigger) ★

**情境**

1. 美术或内容想立刻开做，相关机制还在改。
2. 立项时有一份长设计文档，不知道先做哪个系统。
3. 有人要把后期系统先写成详细规格。
4. 底层做了几轮，想知道什么时候能加下一个系统。
5. 新角色或新系统的能力清单很长，不知先做哪几项。

**语言信号**

- 先做什么 ／ 动画现在能做吗 ／ 这个后面再说 ／ 哪个系统风险最大 ／ 这个角色的技能先做哪几个
- what to build first ／ dependency ／ dependency stack ／ cascading uncertainty ／ build order ／ rework

**与相邻卡的区分（初稿）**

- 核心玩法是什么、设计文档怎么组织、营销要提前定 → `sylvester-core-and-backlog.md`
- 灰盒做哪些、美术何时进来 → `sylvester-graybox-and-art-timing.md`
- 计划做多远、用什么流程 → `sylvester-process-and-planning-horizon.md`

## E — 执行 (Execution)

### 先选分支

| 你的问题像…… | 走 |
|---|---|
| 两个元素谁先定；动画、美术、关卡现在能不能开做 | 分支 1 |
| 整款游戏先做哪些系统 | 分支 2 → 3 → 4 |
| 上层设计现在写细值不值 | 分支 3（先有栈） |
| 底层做了几轮，何时加下一个 | 分支 4 |
| 一个角色或系统先做哪几项能力 | 分支 5 |

### 分支 1：依赖判断与推迟内容（u13-01）

- **输入**：一对元素 A、B，各自是纸面、灰盒还是成品。
- **步骤**：
  1. 问「A 的设计改了，会不会迫使 B 改」，会就记 B 依赖 A；反方向再问一次（p.323）。完成标准：两个方向各有答案和理由。
  2. 只看改动是否迫使对方改，「A 会影响 B」不算（p.326）。
  3. B 依赖 A、A 未定：暂缓 B 的终稿内容，先在灰盒里定住 A（p.324）。完成标准：暂缓清单。
- **判停 / 转向**：A 何时算定住，原书未说明，作者只说底层迭代、试玩几次后更确定（p.330）。
- **输出**（约定）：表，列为「元素对 / 依赖方向 / 理由 / 暂缓的内容」。

### 分支 2：画依赖栈（u13-02）

- **输入**：现有设计（纸面或已部分实现）。
- **步骤**：
  1. 拆成机制、操控、界面、子系统等元素（p.324）。完成标准：元素清单。
  2. 用分支 1 的问句标依赖并估强弱：一方改动几乎必然影响对方为强，只在某些情况下影响为弱；循环依赖保留较强的方向（p.327）。完成标准：依赖表附强弱理由。
  3. 刻意丢掉最弱的依赖（p.327）。完成标准：被丢依赖清单。
  4. 排成栈，每个元素在它依赖的元素之上，底层不依赖任何东西（p.326, p.330）。原图缺失（转换时丢失），按正文重建。
- **判停 / 转向**：弱到什么程度可以丢、循环取哪个方向，原书只有上面的定性对比，交设计者判断。别想画全：要忽略一些依赖，否则陷入分析瘫痪（p.327）。细节不同，同一组标题会画出不同的栈（p.327–328），在输出里写明栈不唯一。
- **输出**（约定）：元素清单、依赖表、被丢的弱依赖、分层的栈。

### 分支 3：级联不确定性估算（u13-03）

- **输入**：分支 2 的栈；设计者给每个元素的确定性。没给先问，不替他估。作者的经验估计：很不原创的设计 80%，冒险的突破性设计常低于 30%，纸面 40% 的设计经几轮试玩可到 90%（p.328–330）。
- **步骤**：
  1. 目标元素原样存活的概率 = 自身确定性 × 它下方每个元素的确定性；下方元素取并集，每个只乘一次（约定：由 p.329 的例子推出，原书没有明说；例中角色同时在战斗和建造之下，只算一次）。完成标准：每个元素一个概率和算式。
  2. 按概率排序，低概率的上层元素列为 backlog 候选，交 `sylvester-core-and-backlog.md`（p.330–331）。
  3. 底层实现、试玩后重估（如 60% 到 90%）并重算（p.331）。
- **原文措辞**：原文说哥布林袭击依赖「five foundational elements」，0.8 乘了五次，但列出的底层只有角色、建造、城墙、战斗四个。单元复核据「80% 只覆盖哥布林袭击自身」一句，把第五个因子读作目标自身，本分支照此计算。两种说法都在原文里，栈图原图缺失（转换时丢失），无法用图核对。
- **判停 / 转向**：截断线原书未说明。作者自称选择是 judgment call，只说该例中三项之上在纸面阶段会低于 50%（p.331）。
- **输出**（约定）：表，列为「元素 / 自身确定性 / 下方元素 / 存活概率 / 是否 backlog 候选」。

### 分支 4：自底向上迭代（u13-04）

- **输入**：栈；各层现状（纸面、已实现、试玩过几轮）。
- **步骤**：
  1. 只实现栈底不依赖任何东西的部分（p.330）。
  2. 迭代、试玩几次，直到足够确定（p.330, p.332）。
  3. 每轮之间做晋级检查，列作者的考量：试玩过几轮、确定性升了多少（例中 40% 到 90%，作者的经验估计）、上面还没有东西依赖它所以改了无妨、清楚要在什么之上建（p.330–332）。完成标准：检查记录。
  4. 稳了再从 backlog 挑一项看起来合适的放上栈顶（p.332）。
  5. 允许栈顶随新知识重组，每次稳固就重复（p.330, p.332）。
- **判停 / 转向**：何时晋级、挑哪项，原书只有「choose something that looks right」，交设计者。意外仍会摇动整个结构，按顺序做只降低频率和冲击（p.330）。
- **输出**（约定）：表，列为「阶段 / 本阶段的元素 / 晋级检查记录」。

### 分支 5：单个系统或角色的小规模栈（u13-08）

- **输入**：能力和子系统清单；它的角色定位。写不出定位先问，没有定位就选不了核心。
- **步骤**：
  1. 列能力，标依赖，排成小栈（p.334–335）。排栈：原图缺失（转换时丢失），按正文重建。
  2. 每项写不确定性标签（只写定性档，不打分）和来由。作者在 Capp 上用过的来由：照搬成熟做法、主要在调参；设计直觉担心太挫败；物理移动、AI 寻路、操控等技术风险；下层传来的级联不确定（p.335）。这是例子，不是穷举。
  3. 选能履行定位的最小核心：有用，且和其他角色不同（p.335）。
  4. 其余液化进 backlog；核心迭代几次够确定了再取（p.335–336）。
- **判停 / 转向**：核心何时够确定，交设计者。作者说细节不同栈就不同，速度和蹬墙跳就可以互换（p.335）。
- **输出**（约定）：小栈、标签表（能力 / 依赖 / 不确定性档 / 来由）、核心与 backlog 清单。

## B — 边界 (Boundary)

**不要用这张卡**

- 问的是核心玩法、设计文档组织、对外承诺 → `sylvester-core-and-backlog.md`。
- 高度衍生的设计：作者说几乎可以不讲顺序（p.328）。

**作者警告的失败模式**

- 底层未定，先做依赖它的终稿内容，底层一改好工作作废（p.324）。
- 假设没有不确定性，按任意顺序做，指望最后像拼图一样合上（p.328）。
- 把上层写成详细规格：级联不确定让它们大多是空话（p.329）。
- 想把所有依赖都分析清楚，陷入分析瘫痪（p.327）。

**作者盲点与时代局限**

- 确定性都是主观估计，80%、30%、40% 到 90% 都是作者的经验数字；连乘隐含各元素失败相互独立，原文未讨论（我的判断）。
- 「上层几乎总要大改」是未经系统验证的经验断言（p.329，批判节）。
- 依赖有强弱（p.327），分支 1 的二元判断是简化；栈还刻意忽略弱依赖和循环依赖。
- 例子默认有长篇纸面设计的中大型团队。
- 分支 1、3、5 各只有一个虚构例子：分支 1 是跑速 5 km/h 改 7 km/h 后动画全部重做（p.324），分支 3 只有 Fantasy Castle 的哥布林袭击（p.328–329），分支 5 只有 Capp（p.334–336）。

**原图缺失与原文不一致**

- 原图缺失（转换时丢失）：Fantasy Castle 依赖栈图（p.326），只能还原正文写出的主链，卡里不复原 22 个元素的排法；Capp 的栈图和核心图（p.335–336）。
- 哥布林袭击「五个底层元素」与只列四个的措辞冲突，见分支 3。
- Fantasy Castle 起步三项前后不一致（p.330 城墙，p.331–332 农耕）。
