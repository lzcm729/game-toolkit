# 核心玩法与设计 backlog

> **怎么用这张卡**：它是方法和书中依据的来源之一，不是回答的模板。回答围绕用户的处境：先给你自己的专业判断和具体做法，书外的实操（算一个例子、查数据、估成本）照常给；再用这张卡补方法、校正判断。不要按卡的分段复述这本书；卡里没写的，不等于不能答。书名和页码只在用户要出处时给。

## R — 原文 (Reading)

> CORE GAMEPLAY is what emerges from the irreducible mechanics of a game at the bottom of its dependency stack. Remove everything that can be removed without making a game emotionally worthless, and what’s left is core gameplay.
>
> 译：核心玩法，是从游戏依赖栈底部那组不可再删的机制里涌现出来的东西。把所有删了也不会让游戏在情绪上变得毫无价值的部分都删掉，剩下的就是核心玩法。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies / Core Gameplay, p.332

> The DESIGN BACKLOG is an unordered, liquid reservoir of ideas, concepts, and impressions that aren’t being worked on and won’t be worked on soon.
>
> 译：设计 backlog 是一个无序、液态的蓄水池，装着眼下没在做、近期也不会做的想法、概念和印象。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies / The Design Backlog, p.330

> If the decision is high in the stack and very detailed, the business or marketing benefit of providing these extremely early decisions might not outweigh the cost of making them so early.
>
> 译：如果这个决定在栈里位置高、又非常细，这么早给出决定带来的商务或营销好处，可能抵不上过早决定的代价。
>
> — Tynan Sylvester, *Designing Games*, Ch13 Dependencies / Dependencies and External Design Needs, p.336

## I — 方法骨架 (Interpretation)

这张卡回答「游戏靠什么成立、设计文档怎么放」。核心玩法的判据是情绪上是否还有意义，不是卖点或循环图：一刀刀删，删到不再产生有意义的体验，撤回最后一刀（p.332）。核心是依赖栈的底座，先把它做出来，就最快得到能试玩迭代的平台（p.333）。

其余想法不连成互锁的详细设计，因为那暗示了我们没有的确定性，而且多半会被底层的变化推翻（p.330–331）。它们拆成互不链接、不排序的条目放进 backlog，只有马上要做的部分连进正式计划。

分支 1 找核心，分支 2 定从哪个核心起步、做完后要不要重来，分支 3 把文档重组成「近期计划 + backlog」，分支 4 处理营销、商务要求提前定的设计。分支 1、2 常连用，3、4 可单独进入。为什么上层不确定、底层稳了何时往上加，见 `sylvester-dependency-stack.md`。

作者观点：核心好就是游戏好，核心糟就是游戏糟，其余只是变化和打磨（p.333）。

## A1 — 书中案例 (Past Application)

- **分支 1｜Civilization V、Unreal Tournament、StarCraft II（例题，p.332–333）**：核心分别是地图、城市、开拓者、战士；地图、第一人称操控的玩家、一把枪；地图、指挥中心、农民、机枪兵。Unreal Tournament 最流行的玩法之一 InstaGib 只留一把秒杀枪。作者的经验估计：现代电子游戏常能删掉 95% 以上；跳棋几乎删不动，象棋只留兵也能玩。
- **分支 2｜点击冒险与 Fallout 3（转述，p.333–334）**：点击冒险没有真正的核心，靠内容而不是机制运作，是例外。Fallout 3 有三个可能的核心（角色加枪加怪物、角色加对话加任务、角色加开放世界加世界美术），设计者可以从任一个起步再往外扩。
- **分支 3｜Fantasy Castle 重组（例题，p.330–332）**：22 个子系统里 19 个液化进 backlog，只把角色、建造、农耕连进正式计划，这三项本身就是一个最小但可玩的游戏。作者说选社区建设是他的判断，换个设计者可能选战斗或宗教。重组后的图原图缺失（转换时丢失）。原书未说明结果。
- **分支 4｜Capp 的扫腿闪避（例题，p.336）**：扫腿在 Capp 小栈的顶端，很可能被级联改动扭曲，迭代之前不值得拿去做广告。

## A2 — 触发场景 (Future Trigger) ★

**情境**

1. 立项或原型评审，要说清这个游戏到底靠什么成立。
2. 原型做出来不好玩，在纠结继续改还是推倒重来。
3. 设计文档几十页、系统互相引用，底层一改就要改一大片。
4. 会上冒出新点子，不知道往哪放；有人要给想法池排优先级。
5. 发行、营销或投资方要提前定预告片或合同里的特性。

**语言信号**

- 核心玩法是什么 ／ 最小可玩版本 ／ 原型不好玩要不要重来 ／ 设计文档怎么组织 ／ 想法池 ／ 发行商要我们先定 ／ 预告片放什么
- core gameplay ／ core loop ／ design backlog ／ design doc ／ restart the prototype ／ marketing wants features locked

**与相邻卡的区分（初稿）**

- 先做哪个系统、算上层存活概率、何时加下一个 → `sylvester-dependency-stack.md`
- 和竞品比、做哪几个特色 → `sylvester-market-value-focus.md`
- 标题和宣传会给玩家什么预期 → `sylvester-purpose-and-expectations.md`
- 一个机制值不值得加 → `sylvester-mechanic-cost-elegance.md`

## E — 执行 (Execution)

### 先选分支

| 你的问题像…… | 走 |
|---|---|
| 这个游戏（或一款已有游戏）的核心是什么 | 分支 1 |
| 有候选核心了，先做哪个；做出来不好要不要重来 | 分支 2 |
| 设计文档太大、互相锁死；新点子往哪放 | 分支 3 |
| 外部方要提前定设计 | 分支 4 |

### 分支 1：删减练习找核心

- **输入**：一款熟悉的游戏或自己设计的元素清单。
- **步骤**：
  1. 删一样，再删一样，依次往下删（p.332）。完成标准：每刀记下删了什么。
  2. 每刀之后判断还能不能产生有意义的体验（p.332）。完成标准：每刀写「仍有意义 / 不再有意义」及理由。
  3. 删到变成琐碎无趣的软件为止，撤回最后一刀，剩下的就是核心（p.332）。
  4. 可对照作者的例子校准（p.333）。
- **判停 / 转向**：「有意义」只有定性描述，由设计者判断。删的顺序原书未说明，而作者承认一款游戏可以有多个核心（p.333），换个顺序可能得到另一个核心，要在输出里提示。练习靠心里推演，作者说好的过程要少依赖心智模拟（p.275），所以结论只是候选，要做出来试玩，转分支 2。内容驱动的类型（如点击冒险）作者说没有真正的核心（p.333），本分支不适用。
- **输出**（约定）：删减记录，列为「第几刀 / 删了什么 / 是否仍有意义 / 理由」，加一个候选核心。

### 分支 2：以核心起步

- **输入**：候选核心（来自分支 1）；游戏是机制驱动还是内容驱动。
- **步骤**：
  1. 有多个候选时选一个起步，写明理由（p.333–334）。作者称这是 judgment call（p.331）。
  2. 最先把核心做出来，尽早得到能试玩迭代的平台（p.333）。
  3. 核心第一轮试玩后做重来检查，列作者的考量（p.333）：核心好坏就是游戏好坏；找不到核心或做出来很糟，就考虑换个方向重来；没有强核心要有很好的理由，内容驱动的类型（如点击冒险）例外。完成标准：检查记录。
  4. 核心做好后从 backlog 取一项放上去，往外迭代（p.333），后续顺序见 `sylvester-dependency-stack.md` 分支 4。
- **判停 / 转向**：什么算很糟、何时重来、多个核心选哪个，原书未说明；「consider restarting」是建议不是规则，交设计者。
- **输出**（约定）：起步记录，列为「候选核心 / 选定的核心及理由 / 第一轮后的重来检查」。

### 分支 3：把设计文档重组成近期计划 + backlog

- **输入**：设计文档的元素清单；设计者认定哪些马上要做。
- **步骤**：
  1. 分成两部分：马上要做的，近期不做的（p.331）。
  2. 只把马上要做的部分互相链接、写细，纳入正式计划（p.331）。
  3. 其余液化：拆成互不链接、不排序的条目，放进 backlog（p.330–331）。完成标准：条目之间没有交叉引用。
  4. 新想法一来就写进 backlog，然后先忘掉；接受大部分条目永远不会实现（p.332）。
- **判停 / 转向**：「马上要做」看多远、条目写多细，原书未说明，作者说留哪些在计划里是 judgment call（p.331）。不给 backlog 排优先级、估点数：名字借自 Scrum，但作者明说它不属于正式流程，只是保留灵感的非正式工具（p.330）。何时从池里取，见 `sylvester-dependency-stack.md` 分支 4。
- **输出**（约定）：正式计划（近期元素及其链接）、无序的 backlog 列表、每个原有元素的去处。

### 分支 4：外部方要提前定的设计决定

- **输入**：对方要提前定的每个决定；依赖栈。没有栈先走 `sylvester-dependency-stack.md` 分支 2 或 5。
- **步骤**：
  1. 找到每个决定在栈里的位置（p.336）。
  2. 看它有多细（p.336）。
  3. 位置高又很细的标出来：这么早定下的营销或商务好处可能抵不上代价，建议迭代之前不对外宣传、不锁死（p.336）。完成标准：每个决定有高度、细节两项标注。
  4. 和要这个决定的人协商一个中间地带（p.336）。
- **判停 / 转向**：好处和代价怎么比、中间地带长什么样、怎么谈，原书未说明；作者在书目里推荐 Getting to Yes（p.378）。
- **输出**（约定）：表，列为「决定 / 栈中高度 / 细节程度 / 是否高且细 / 建议」，作为协商立场。

## B — 边界 (Boundary)

**不要用这张卡**

- 问的是系统先后、上层存活概率 → `sylvester-dependency-stack.md`。

**作者警告的失败模式**

- 把还不做的点子连成互锁的固定计划，为它们付出大量工作，又随底层变化一起失效（p.330–331）。
- 把仍在迭代、在栈顶的细节特性对外宣传，之后改不动；作者说不要把设计锁进不可更改的牢笼（p.336）。

**作者盲点与时代局限**

- 作者偏向机制驱动的游戏，叙事或内容驱动的游戏只当例外（p.333）；线性叙事类的适用性要另外判断（编者评注「最强反对意见」）。
- 「现代电子游戏可删掉 95% 以上」是作者的估计；多核心只有 Fallout 3 一例。
- 分支 4 唯一的例子是 Capp 的扫腿闪避，没有量化好处与代价的方法。作者承认这要每天花力气，起初不是人人理解（p.336）。
- 跨章条件：第 10 章说营销决定和设计一样影响游玩体验，要把营销人员当作体验团队的一员（p.266）；第 11 章说规划不足会让营销、投资、招聘、渠道等外部方拿不到信息（p.280）。和分支 4 一起看。
