# 共享分层定义与实现契约

本文件是三件套 agent 与 `split-doc-layers` 的分层定义真值源。它定义职责和交付判据，不指定项目目录、语言或引擎，也不要求每个格子各建一份文档。已有契约用指针复用。

## 两条正交轴

**引擎耦合度轴：**

- **A：游戏语义与实现契约** — 规则、状态转换、不变量、设计判据；依据项目目标与明确的游戏语义。执行者不需要补做规则设计。
- **B：工作流与任务编排** — 收集上下文、分工、管理产物、同步状态与验证证据；不能通过派活或文档拆分改变规则。
- **C：技术适配与执行** — 源码定位、引擎对象映射、代码/数据实现、构建、运行与采集；由项目 / 技术适配提供具体承载方式。

**游戏职责轴：** Framework = 游戏怎么运转；Content = 游戏里有什么；Interface = 玩家如何输入意图、获知状态与结果。Interface 包含交互与呈现，不泛指所有玩法设计；组件名保留 `interaction`，语义职责统一称 **Interface**。

| 游戏职责 | A：必须保留的契约 | B：编排产物 | C：由项目 / 技术适配提供 |
|---|---|---|---|
| Framework | 权威状态、命令、规则、执行顺序、拒绝、领域事件、不变量 | 规则依赖、契约缺口、验收与交接状态 | 状态的技术承载、调度/事务机制、代码位置、构建与运行命令 |
| Content | 实例身份、字段含义/单位/范围、关系、叙事条件、资源语义及平衡目标 | 内容清单、真值源指针、校验与资源交接 | 序列化/schema 映射、数据与资源路径、导入器、脚本语言与生成命令 |
| Interface | 输入到命令的映射、局部交互状态、可见性、反馈时序、取消与可达性 | 输入/结果覆盖、体验验收与交接 | 设备绑定、视图/场景对象、渲染/动画/音频载体、代码路径与采集命令 |

三者都贯穿 A/B/C。不能把 Framework 整体当 A、Content 当数据适配、Interface 当纯渲染，也不能用 hooks、reducers、组件或文件扩展名决定游戏职责。

## 边界与缺口处理

- Framework 拥有权威游戏状态及其改变规则。Content 提供契约允许的实例/参数/声明式组合，可校验内容格式与约束，不能另写游戏资格校验、扣款、奖励或执行顺序；新操作符、新状态类型、新失败分支先回 Framework 明确定义。
- Interface 拥有焦点、选择、输入草稿、待确认反馈等局部状态，可以请求命令、呈现结果；不能裁决余额是否足够、是否扣款或撤销已提交的游戏结果。Content 的提示文本不能改变拒绝条件。
- 允许实现共处一个文件；按语义所有权约定编辑区段和交接，不能因技术共址争夺规则，也不能以文件名拒绝属于本职责的工作。
- 已有契约先引用并核对。缺失语义由对应职责的设计工作补全、列明来源及待定项；同一个 agent 可以先完成 A 再做 C，但不能在适配时暗自决定行为。只阻塞依赖该缺口的实现，独立工作可继续。
- 技术能力不满足契约时，报告缺少的能力及受影响场景，回到设计决策；不能悄悄弱化原子性、确定性、权威性或时间要求。

## A 层交付门槛

每项变更引用或补齐下表中相关内容；不适用项说明理由。不能只写“管理状态”“处理失败”。

| 契约项 | 可实施的粒度 |
|---|---|
| 状态与所有权 | 列出状态字段、含义、初值/范围、谁能读写、权威边界、生命周期及持久化/恢复要求 |
| 命令与前置条件 | 输入及单位、合法范围、权限/阶段限制、前置条件检查顺序；区分查询、预演与提交 |
| 转换与原子性 | 给定状态如何变到下一状态；中间态是否可见、哪些变化同成同败、冲突顺序与重入/重复请求策略 |
| 拒绝与恢复 | 稳定原因、同时失败时的优先级、拒绝后哪些状态不变、重试/取消/回滚边界 |
| 事件与副作用 | 事件含义及载荷、产生时点/顺序、交付与去重语义；存档、通知、动画、音频等何时可发生、失败是否影响已提交结果 |
| 不变量与判据 | 始终成立的关系、允许的实现差异；以具体初态→操作→终态/事件/禁用副作用验收，覆盖失败和竞争 |
| 跨职责接缝 | Framework 的命令/结果，Content 的字段/实例，Interface 的输入/反馈引用同一契约，明确缺口由谁补 |

**执行模型必须显式声明，按机制需要保留能力：**

- 时间：逻辑时间或真实时间、时间单位、固定时间步及步长（如需要）、更新顺序、暂停/时间缩放、超时和跨步处理；不得用引擎默认更新回调暗定规则。
- 空间与连续运动：坐标系/原点/轴向、距离与速度单位、积分/碰撞判定顺序及容差；渲染插值是否只影响显示。
- 确定性与网络：是否要求确定性模拟、随机源/种子与消耗顺序、数值精度、权威端、命令排序/迟到策略、预测与校正边界。支持这些概念，无须为了通用而降成单机逐帧模型。
- 动画与音频：触发依据是输入、预测还是已提交事件，时间基准、相对顺序/延迟容差、打断/循环/暂停规则；若动画标记影响命中，命中时刻须成为 Framework 契约，不能由素材默认长度决定。

## 粒度示例：购买与 PlanPurchase

以下是一个**示例游戏的既定设计**，用于展示交付粒度；不作为其他游戏的默认购买规则。

**状态与内容：** Framework 的权威端拥有账户余额 `balance`（整数代币，初值由开局配置给定且 ≥ 0）、仓库 `owned[itemId]`（非负整数，缺项视为 0）、容量 `capacity`（非负整数物品槽位，一个物品占一位），以及账户内唯一的 `requestId → 输入/结果` 记录。初始占用不得超容量。购买目录是 Content 提供的会话内不可变快照：唯一物品 ID、正整数单价；缺字段/非法值拒绝加载该快照，不能默认补 0。会话开始时已有有效快照才开放购买。

**命令与预演：** 认证账户发送 `Purchase(requestId, itemId, quantity)`。纯函数 `PlanPurchase(state, catalog, input)` 按下列顺序判定，返回拒绝原因或包含总价及前后状态的方案；它不改状态、不预留余额、不发事件。预演成功不保证以后提交成功。

1. `quantity` 非正整数 → `InvalidQuantity`。
2. 物品不在目录 → `UnknownItem`。
3. `balance < price × quantity` → `InsufficientFunds`。
4. `sum(owned) + quantity > capacity` → `CapacityExceeded`。
5. 否则方案为扣除总价、增加对应数量。金额采用精确整数语义，不允许溢出绕过检查。

**提交、并发与重复：** 认证失败直接拒绝 `Unauthorized`，不读取账户结果。权威端对同一账户按接收序号串行处理（序号唯一）；先查 requestId：同 ID 同输入返回已记录结果，不再执行；同 ID 不同输入拒绝 `RequestConflict`，不覆盖记录。新 ID 在当前状态重新执行 `PlanPurchase`，不能直接套旧预演。成功时余额、仓库、成功记录及领域事件同一次原子提交，对外无“已扣钱未到账”中间态。业务拒绝仅记录拒绝结果，不改余额/仓库；同 ID 重试仍得该拒绝，新尝试须换 ID。

**事件、副作用与恢复：** 成功产生一个逻辑事件 `PurchaseCompleted(accountId, requestId, itemId, quantity, totalPrice)`，按提交序发布；业务拒绝无领域事件。余额/仓库、请求结果及待发布事件持久化并共同恢复，请求记录保留整个账户生命周期，恢复后仍可去重。持久化提交失败则整体不变、无成功事件，返回可重试的 `Unavailable`，不记录业务结果。提交后发送失败只重试交付，不重新购买；传输允许重复，消费者按 `(accountId, requestId)` 去重，成功音效/通知只消费一次。Interface 可以立即展示等待状态，成功反馈只能来自权威成功结果；关闭界面不取消已接收命令或撤销提交。

**不变量：** 余额和物品数量非负、占用不超容量；成功前后代币差等于总价，物品差等于购买量；一个请求最多扣一次、加一次、产生一个逻辑成功事件。

**具体验收：** 除特别说明，各场景独立从余额 100、已拥有 0、容量 2、单价 60 开始。

| 操作/条件 | 必须观察到的结果 |
|---|---|
| 仅调用 PlanPurchase 预演买 1 个 | 返回余额 40、数量 1 的方案；实际余额仍为 100、数量 0，无请求记录或事件变化 |
| 新请求买 1 个 | 余额 40、数量 1、一个总价 60 的成功事件；提交后才有成功反馈 |
| 新请求买 2 个 | `InsufficientFunds`；余额 100、数量 0、无成功事件/音效 |
| 余额 200、容量 0，买 1 个 | `CapacityExceeded`，游戏状态不变 |
| 数量 0 且物品不存在 | `InvalidQuantity` 优先；无游戏状态变化 |
| 两个不同 ID 并发各买 1 个 | 接收序号较小者成功，另一个 `InsufficientFunds`；最终余额 40、数量 1 |
| 成功后同 ID 同输入重试；再同 ID 改数量 | 先返回原成功结果，再返回 `RequestConflict`；均不再扣款或发新事件 |
| 买 2 个被拒绝后，余额通过其他既定机制增至 200，再用同 ID 重试 | 仍返回原 `InsufficientFunds`，余额保持 200、数量 0；新 ID 才可重新判定 |
| 预演成功后另一请求先花掉 60，再提交原请求 | 重新判定为 `InsufficientFunds`，不套用过期方案 |
| 提交持久化失败；或提交后断线再重试 | 前者状态全不变且无成功事件，可同 ID 重试；后者返回已存结果且只扣一次 |

Content 只能改本例允许的实例及开局参数，不能另定扣款规则；Interface 映射输入、等待/拒绝/成功反馈，不能把按钮禁用当作权威校验。存储结构、引擎对象、线程/队列实现可不同；上述状态、顺序与可观察结果必须相同。

## 项目环境声明

C 层的事实由**项目声明**，不由工具探测。声明放在项目根的 **`game-toolkit.yaml`**，
本插件所有组件从这里读；CLAUDE.md 里留一行指针即可，不要另写一份。

**为什么是独立 YAML 而不是 CLAUDE.md 的一段**：这份声明既给 agent 读，也给程序读
（`project_env.py`，以及将来任何需要知道工程根与技术栈的工具）。用 Markdown 列表
承载就得靠正则去啃，人改一下排版就解析不出来。严格格式换可靠解析。

**引擎与引擎版本必须人工填写。** 探测能认出 `project.godot`，但认不出
「这个仓库里哪个才是本次要动的工程」「用的哪个大版本」「Blueprint 能不能按文本扫」。
猜错的代价——把查不了的东西报成缺失、按错误的路径规则生成资源——远大于问一句。

```yaml
# game-toolkit.yaml（项目根）
engine: unreal
engine_version: '5.8'
project_root: .
tech_stack: C++ / Blueprint
source_scope: Source/ 下的 .cpp / .h；Content/ 为资产，不计入文本扫描
inspectability: C++ 可按文本扫；Blueprint / .uasset / .umap 查不了，不得据文本结果判定缺失
verify_entry: 尚未登记，使用前读项目构建说明
```

**必填**（缺了就问用户，不要用默认值顶替）：

| 字段 | 说明 |
|---|---|
| `engine` | `godot` / `unreal` / `unity` / 自研 / `无`（纯文档项目） |
| `engine_version` | 具体版本号；确实不知道写「待核实」，不要留空 |
| `project_root` | 相对 `game-toolkit.yaml` 的路径。仓库根 ≠ 工程根时尤其要写 |

**可选**（缺了按「未知」处理）：`tech_stack`、`source_scope`、`inspectability`、`verify_entry`、`asset_config`。
已有 Architecture 或构建文档就引用它们，不要复制出第二份真值。

**三种「没有」必须分开写**，不能混成一句「不支持」：

| 写法 | 含义 | 后果 |
|---|---|---|
| 未知 | 还没查，可能有 | 需要时去查或问 |
| 不适用 | 这个项目结构上就没这一项 | 跳过，不报缺 |
| 查不了 | 有，但当前手段验证不了 | **不得当作「未实现」** |

最后一条是硬要求：把「查不了」报成「未实现」会引发重复实现。Blueprint 逻辑、
预制体连线、可视化脚本都属于这一类——文件能 Glob 到，内容读不懂。

### 从 3.3.0 的 Markdown 声明迁过来

3.3.0 曾把声明放在 CLAUDE.md 的 `## Game Toolkit 项目环境` 段落里。脚本**只认
`game-toolkit.yaml`**，所以那种项目会被报成「没有声明」。迁移手动做，三步：

1. 读 CLAUDE.md 里那段的字段值（`- 引擎：unreal` 这样的列表项）
2. 用 `write` 把它们写进 `game-toolkit.yaml`，逐条核对转换结果
3. 把 CLAUDE.md 里那段换成一行指针，**不要两边都留** —— 双份真值必然漂移

两边都存在且不一致时，以 `game-toolkit.yaml` 为准并报告冲突，不要默默选一边。

### 怎么拿到这份声明

有脚本，别手抄：

```bash
python <本 skill>/scripts/project_env.py check <项目根>     # 只读，输出 JSON
python <本 skill>/scripts/project_env.py write <项目根> --engine unreal --engine-version 5.8 ...
```

**脚本不与人交互，也不该交互** —— 它在 Bash 工具里跑，stdin 接空设备，`input()` 只会拿到 EOF。
分工固定成三步：

1. `check` —— 报告缺哪些必填项，并给出**探测到的候选值**（`.uproject` 的
   EngineAssociation、`project.godot` 的 config/features、源码构成、二进制资产数量…）
2. **主流程用 AskUserQuestion 把候选值交给人确认** —— 这一步不能省，而且只能由主流程做：
   三件套等实现 agent 的 tools 里**没有** AskUserQuestion，它们问不了。**顺序是
   「主流程 check → 问人 → write → 再委派」**，委派时把已确认的事实一并传下去；
   子 agent 发现缺口时把结构化缺口交回主流程，不自行发起确认。探测认得出
   `.uproject`，认不出「一个仓库里哪个工程才是本次要动的」「EngineAssociation 是版本号
   还是源码版引擎的 GUID」「Blueprint 能不能按文本扫」。预填候选让人确认，不是让人从零填。
3. `write` —— 把确认后的值写回 `game-toolkit.yaml`。整文件重渲染（注释每次都在），
   合并已有字段，**用户自己加的未知字段原样保留**，可反复跑。

`check` 的输出里 `detected` 一律是候选，`declared` 才是已确认的事实。
两者冲突时报告冲突，不要默默采信探测值。

**读取顺序**：本次任务明确指定 > 项目声明 > 项目内已有技术文档 > 问用户。
**任何一环都不猜引擎。** 声明与本地证据冲突时报告冲突，不要默默选一边。

**几条边界**，免得这份声明被当成它不是的东西：

- 它是兜底事实，不是能力白名单。缺某个字段不妨碍完成不依赖该字段的任务。
- 只读本次任务要用的字段。生成普通图片不需要先解决构建入口。
- 独立子 agent **不会**因为主流程读过声明就自动拥有它——委派时要把工程根、
  相关字段和它们的来源一起传过去；worktree 里的路径要重新绑定到该 worktree。
- 声明变化导致扫描范围变化时（新增目录或文件类型），依赖增量水位的流程
  必须触发一次全量对账，否则新纳入的文件会一直被跳过。

## C 层交接与四问自检

技术适配记录放在项目已有技术说明或实施产物中，标明**“由项目 / 技术适配提供”**：契约符号→源码位置/引擎对象映射、数据/资源格式、工具链和命令、能力满足方式、运行与采集证据。A 中只引用该记录，不以具体路径或命令定义游戏规则。

交付前按具体场景回答：

1. **换引擎，状态转换和验收场景是否仍成立？** 允许改变承载方式，不应重写游戏行为。
2. **执行者能否不重新设计规则就实现它？** 任一字段、优先级、单位或时序仍需猜测，则退回所属职责补契约，不能只补一句概述。
3. **失败路径、并发、副作用是否有明确约束？** 验收须能观察到拒绝后的状态和禁止发生的效果；不适用时写原因。
4. **两个实现不同，能否据契约判定哪些差异允许？** 对可观察行为、数值/时间容差及技术自由度给出边界。
