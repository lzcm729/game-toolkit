# split-doc-layers — 设计文档职责拆分

## 共享定义与调用模式

先用 Skill 工具调用 `game-toolkit:layer-contracts`，它是 A/B/C 与 Framework/Content/Interface 两条正交轴、职责边界及契约门槛的唯一共享定义。下文的“Content 层”等沿用游戏职责轴的简称，不是引擎耦合度层。组件名仍为 `interaction`，语义职责统一称 Interface。

**实际拆文档时**：按下述流程执行。职责拆分不能丢失 A 层契约，尤其不能把失败条件、并发/原子性、时空单位及副作用时点当技术细节移走。遇到语义缺口标明所属职责，拆分本身不补造规则。

把混写了机制算法、实例清单、精确数值的设计文档按职责拆开管理。
Content 层（里面有什么）与 Framework 和 Interface 耦合最低，最适合先拆。

**核心定位**：读项目配置 → 区分读者目录与作者工作台 → Phase 0 判断该不该拆 → Phase 1-5 执行拆分 → 沉淀 lessons。
项目特化（数据路径、读者设定、指针位置等）由项目配置与技术适配提供，本 skill 不预制领域字段。

**作者工作台模式**：需要维护实例定义、来源、发布情况与设计意见时，先读 `examples/content-model/README.md`，按实例身份与定位 / 已采纳定义 / 发布情况 / 讨论组织作者模型。业务字段标声明性或解释性；解释性注明 Framework / Interface / C 归属。现有契约仅按 ID 引用；缺家标缺口，不能在内容适配时补规则。

后文 Phase 1/3 的“不手写精确数值”及 checklist 针对独立维护的读者目录。作者工作台可以记录带不可变来源版本、生效方式的声明值；人工核对的快照必须标明人工、覆盖范围与版本，不冒充自动派生或实时真值。作者模型不等于发布 IR，讨论与运行时玩家状态不能成为内容发布输入。用 `scripts/check_content_model.py` 检查结构，不能据通过结果承诺语义、引擎相符或往返。

编辑入口与权属按集合/字段组声明：来源版本、拥有方、提案入口、接受流程、生成目标、生效时机。新增声明先放项目侧，沿用旧配置时不得暗中增键或用单值 `content_truth` 取代分组所有权。

> **职责覆盖**：Phase 1-5 针对 **Content**（拆出独立目录，最适合起步）。**Interface**（输入与反馈）走**不同路径**——它常已有 SSOT（交互契约 / mockup / 设计系统 / spec / 实现），优先索引已有来源，见 Phase 5 后专节《Interface 职责》。

## 启用前置：读项目配置

实际拆分执行任何 Phase 前，先在项目根读 `split-doc-layers.config.yaml`。

**由项目 / 技术适配提供（C 层）**：本配置里的文件位置/格式、领域符号到引擎对象的映射，以及读取、导出、构建、运行和采集命令，从项目配置与技术说明取得；在技术记录中标注并由语义文档引用，不混入职责定义。下表的路径/格式仅是配置示例，不是通用目录约定。

配置 schema 见 `examples/README.md`，共 7 项：

| 配置项 | 含义 |
|---|---|
| `data_ssot` | 既有数值读取定位（如资源/数据文件模式）；有效值仍须按项目来源声明核对字段组、版本、覆盖与默认值，不能仅扫描此路径便推定唯一真值 |
| `framework_docs` | Framework 文档路径模式（如 `docs/GDD/*.md`） |
| `content_dir` | 内容目录位置 + 形态（如 `docs/design/*-menu.html`） |
| `semantic_field` | 数据 schema 里现成的语义字段名（逐字搬源） |
| `reader` | 内容目录目标读者（`designer` / `player` / 自定义） |
| `pointer_loc` | 双向指针两端位置描述（格式 `内容目录端 ↔ Framework端`） |
| `forbid_pattern` | 防回退精确数值正则（标注用，如 `[0-9]+\.[0-9]+`） |

配置文件不存在时，先引导用户参考 `examples/README.md` 建一份，再继续。

## Phase 0 — Guard：该不该拆？

**满足任一跳过条件即跳过拆分（避免形式大于内容）：**

- [ ] DriftPredictor = 文档改频 ÷ 相关代码/数据改频 < 0.2 → 文档已被代码替代，不需拆
  **无 git 历史 / 无法计算时**：用 `{{framework_docs}}` 版本号或修订频率 vs 数据文件字段稳定性做定性比较；或直接跳过此条，用下方"可继续的信号"判断——DriftPredictor 是辅助信号，不是硬门槛。
- [ ] 目标系统的 Content 层不厚（实例 < 3 个，且无独立描述价值）→ 机制驱动型，保留在 Framework 文档即可
- [ ] 数值本身即 content 主体（纯数值对比表/参数手册）→ 本方法论不适用，见 frontmatter"不适用"

**可继续的信号（满足以下任一即继续）：**

- 文档里有完整实例清单 + 机制算法混写
- 每次调参需要同步文档（漂移已经发生）
- 实例数量 ≥ 3 且实例有独立的描述价值

## Phase 1 — 定读者

从 `{{reader}}` 配置读目标读者，确认内容目录的边界：

| 读者 | 可放 | 不可放 |
|---|---|---|
| **玩家（config reader: player）** | 身份摘要（一句话）、文案、视觉标识 | 规则/技术细节；设计推荐；精确数值 |
| **设计师/开发者（config reader: designer）** | 身份摘要、契约允许的实例条件/组合、规则与技术来源指针；identity 属性（弱点/标签等）；功能组合推荐 | 另写执行规则；精确数值（留 `{{data_ssot}}`）|
| **自定义（config reader: 其他值）** | 参照 designer 规则作默认基准，按描述调整 | — |

同一项目不同内容目录可能目标读者不同——先确认再画边界。

## Phase 2 — 判形态

**先 explore、别套模板**。对每个目标系统独立判断 content 形态：

| 形态 | 适用场景 | 建议文档形式 |
|---|---|---|
| **并列实例型** | 实例多、数量并列（角色图鉴/配料清单/天气清单） | 独立内容目录：卡片式（HTML 图鉴、卡片表） |
| **映射型** | 输入→输出映射（配方表、升级对照） | 表格 |
| **序列型** | 有时序关系（关卡编排/日程表） | 时间线 / 按序号列表 |
| **层级/树型** | 有父子关系（升级树/技能树） | 嵌套结构 / 树图 |
| **机制驱动聚合型** | Content 只是算法参数的聚合，实例本身很薄 | **不强拆**——留在 Framework 文档 |

**关键判断**：content 驱动型（实例多/并列/有独立描述价值）→ 拆独立内容目录；机制驱动型 → 不强做图鉴。

推广多个系统时，逐个 explore，不假设"上一个是卡片所以这个也是卡片"。

**首次拆分 / 要推广到多个系统时：先选一个最典型系统（实例多、最适合卡片）试点，走完 Phase 2-5 + 陷阱 checklist，回审"哪条标准从未被真正用到"，等用户确认后再推广其余系统——逐个 explore，不批量套同一模板。**

## Phase 3 — 提取 Content

**提取前先确定「实例单位」**：明确这个系统的实例是什么维度——个体 / 类别 / 属性档 / 矩阵格子。多维系统尤其要先定（如「物种 × 稀有度」既可按物种、也可按稀有度档、还可按矩阵格子组织内容目录，三种选法结论完全不同）。判断来源：从 `{{framework_docs}}` 的 §2 核心循环 / §3 机制清单找该系统的实例维度；无明确实例清单时，以 §1.2 设计意图的**主线维度**为实例。不同实例单位 → 不同内容目录结构，定错会整份返工。

**进内容目录：**
- 实例清单（该系统所有实例）
- 身份摘要：读者视角"这个实例在做什么"——一句话，不给精确数值；实例条件、来源指针和克制关系按 `{{reader}}` 决定
- 文案（玩家可见的名称/标签/提示文字）
- 视觉标识（图标 id / 颜色分类）
- 关系标签（定性词，非精确数）

**不进内容目录：**
- **精确数值**：hp / 速度 / 倍率等精确数字 → 留 `{{data_ssot}}`（防 stale 漂移）；想给读者量级感用定性档位（"中等血量/速度偏慢"），不写精确数字
- **FIXME 占位值**：尚未校准的值漂移风险更高，尤其不进内容目录
- 执行规则（所有读者）：状态转换、公式、拒绝/原子性、领域事件含义 → 留 Framework 契约，以指针引用；引擎信号名/对象绑定 → 项目技术适配记录
- 临时设计推荐：即兴的克制建议/搭配推荐 → 不写（易 stale）；但数据 schema 已有的 identity 属性可进
- 视觉规格：进度环/飘字动效/颜色 hex 规格 → 留 Interface 层

**身份摘要优先来源**：先检查项目声明的 schema 与 `{{semantic_field}}`，核对字段用途、来源版本和目标读者。可逐字引用已有自然语言描述，但逐字复制只避免本次转述偏差，不证明来源仍准确；展示字符串手抄参数时要记录展示与数值的耦合。

已有字段不适合目标读者（如 `CHASE_IF_DIST_LT_200`）时可提炼，标解释性、责任归属与来源版本。来源描述和当前实现不一致时分开显示，交所属职责裁决，不悄悄择一成为新规则。

**`{{semantic_field}}` 配置为 `none`（无现成语义字段）时的提炼路径：**

1. **从哪提炼**：从 `{{framework_docs}}` 的设计意图段（如 §1.2 体验设计 / §3.1 核心机制描述）提炼，这是最接近"对读者有意义的描述"的来源。
2. **提炼模板**：`[实例名]：[一句话核心身份]（来源：{{framework_docs}} §X.Y）`
   - 示例：`小鸡：孵化速度最快的入门动物，适合新手学习节奏（来源：docs/design/gdd/animal.md §1.2）`
3. **提炼粒度**：多段设计意图压缩为一句身份摘要——不整段搬，提炼"这个实例在玩家/设计师眼中是什么"。
4. **精确数值不进摘要**：用定性档位替代（"孵化最快"而非"孵化需 1 秒"；"稀有度高"而非"稀有度概率 5%"）。
5. **漂移风险标注**：每条提炼摘要旁加注释，格式：
   ```
   <!-- 高漂移：本句从 {{framework_docs}} §X.Y 手动提炼，源文档更新后需同步核对 -->
   ```

**tag 配色规范**：同一语义维度的标签必须同色，只有不同维度才换色。在样式系统里统一定义，不在每张卡片里各自内联。

### 进阶：auto-dump —— 让内容目录从 `{{data_ssot}}` 自动生成

auto-dump = 按项目来源声明读取已接受版本，经适配后生成内容投影。它减少手工复制，但须核对覆盖与脚本默认、字段映射、单位和关系；自动生成本身不证明语义准确。输出应记录生成入口、来源版本及读取范围，重新读取并验证后才可称已同步。

「是否展示精确数值」仍由 `{{reader}}` 与设计意图决定。作者工作台可显示有来源的参数与人工核对快照；读者目录避免另养手写数值副本。作者模型、发布 IR、渲染输出各有字段边界；引擎读写、三方合并与往返证明由项目适配另行实现，不能拿一次格式序列化代替。

**何时值得建**（满足多条再做，否则手动提取够用）：
- 内容目录的数值/字段频繁随调参漂、手动同步成本高
- 实例多到手维护不值（经验阈值 > 20）
- `{{data_ssot}}` 是机器可读格式（文本，或可导出文本）

**引擎无关的 4 步 pipeline：**

```
1 读 {{data_ssot}} → 2 解析成「实例列表」(统一中间表示) → 3 套模板渲染 → 4 写 {{content_dir}}
```

这是处理阶段示意，不按步骤直接划 A/C：第 1-2 步的读取、解析与字段/单位映射由项目 / 技术适配提供，直到形成符合内容契约的实例列表；第 3-4 步可复用渲染与写出骨架，但模板、输出位置与命令仍由项目提供。

**读取/解析适配示例（由项目 / 技术适配提供）：**

| 格式 | 怎么读到「实例列表」 |
|---|---|
| CSV / JSON / YAML | 使用项目支持的解析库，再按字段契约处理类型、单位与引用 |
| Godot `.tres` | 用项目验证过的资源解析/导出方式解析引用与字段；不把文本提取等同完整资源语义 |
| Unreal DataTable | 编辑器 **Export to CSV**（或 Unreal Python API）→ 走 CSV 路径 |
| 其他格式 | 查项目导出能力；不能导出或无法保留语义时，报告适配缺口 |

**关键**：中间表示须保留 ID、字段含义/单位及关系并通过内容契约校验；适配器不能补造缺失规则。能否导出、怎样解析由项目能力决定。

**第 3 步「渲染」按 `{{content_dir}}` 形态**（HTML 图鉴 / Markdown 表…）。渲染时仍守上方 Phase 3 边界（执行规则 / 视觉规格不进，来源指针按读者需要保留）。

**别从零造**：auto-dump 是「数据源 → 生成物」生成器，与本插件 `generate-assets` skill 同构（一个生文档目录、一个生图片）。参考其 `data_source.py` 的数据源加载思路（json_dict / json_list / inline + filter），不重造轮子。

**落地原则**：具体脚本按上面骨架在**项目侧**实现（语言 / 引擎随项目，不进通用 skill）；建成后在内容目录 footer 标注「本目录由 `<脚本>` 从 `{{data_ssot}}` 自动生成，勿手改」。

## Phase 4 — 双向指针

按 `{{pointer_loc}}` 配置，在两端各加一件指针，构成导航闭环即够——不要第三件（第三件=手写中央索引，含代码路径、随文件重构漂移）。

1. **内容目录 → Framework**：footer 或头部说明，链接 Framework 文档 + `{{data_ssot}}`（精确数值在哪）
2. **Framework → 内容目录**：在"速查/快速参考"段加一行"内容目录 → `xxx-menu.html`"（或对应路径）

手写维护的静态中央索引（把所有系统的框架/内容位置集中列在一处）会随文件重构漂移——需要全局总览时，用 Glob/CI 脚本自动生成，不手写。自动生成的总览索引是**永久产物**（手写版的升级形态），推广完成后不删除。

## Phase 5 — Framework 瘦身

拆出 content 目录后，对 `{{framework_docs}}` 做最小改动：

**保留**（不删）：
- 设计意图叙事中的 content 举例（举例是机制说明必需的，不能删）
- 设计禁区 / 体验目标（高层定性描述）
- 机制算法 / 公式
- 共享定义要求的权威状态、命令、拒绝优先级、原子性/并发、领域事件、不变量、执行模型与具体验收；只可引用已有真值源，不得瘦身成“管理状态”

**指针化**（只加，不删叙事）：
- 完整实例清单段 → 加一行指针到内容目录，完整清单本体**不再独立维护**；若保留须注明"以内容目录为准，本段不再独立维护"
- 全数值表 → 加指针到 `{{data_ssot}}`

实践中若 Framework 文档本就不含完整清单，"瘦身"主要就是加指针，改动极轻。

**技术信息另标**：构建/运行命令、源码位置、引擎对象映射标为“由项目 / 技术适配提供”，集中到已有技术段或适配记录并留指针。逻辑时间步、网络权威、运动单位等行为要求仍留 A 层契约；保留它们的验收场景。

## Interface 职责：与 Content 不对称，多是「索引化」非「建目录」

> 上面 Phase 1-5 是 **Content** 的拆分管线。Interface（输入与反馈）**不走同一套**——照搬会造双 SOT。

**关键不对称**：Content 值得拆出独立目录，前提是**拆前无独立家**（语义字段散在 `{{data_ssot}}`、无人类可读投影）。Interface 往往**相反**——它早有自己的 SSOT 群，只是不在 `{{framework_docs}}` 里：

- 输入/反馈契约（输入到命令、局部状态、取消/拒绝、反馈时序与验收）
- 视觉稿（mockup / 设计图）
- 设计系统规范（色 / 字 / 层级 / 动效 token，单份）
- 单屏蓝图（per-screen spec）
- **实现本身**（代码建的 UI，其布局即 SSOT）

→ **Interface 的"拆分"多半是用索引串起已有来源**，不是新建目录。`{{framework_docs}}` 保留反馈意图及 Framework 拥有的命令/结果契约，具体输入/反馈契约引用 Interface 的真值源；不能只留 WHY 而丢掉行为。给已有家的内容再建 catalog = 第 N+1 个 SSOT = 双 SOT。复用 Phase 0 判据：对每个候选 Interface 产物问"拆前有没有独立家"——有家则只索引、不新建；确实无家且同质并列（罕见）才考虑 content 式目录。

> ⚠️ 实战教训：覆盖审计常把"没有 spec 文件的 UI"误报为"待补盲区"，但它的设计意图可能记在别处（决策档 / 实施 plan / 代码头注释），布局真值就在实现里。**写新 spec 前必先核实它是否已有家**——否则写出的就是违规重复 SOT。

**布局存在不等于契约完整**：已有代码可以是布局真值，但不能替代输入命令、失败/取消、权威结果和反馈时序的语义约束。先查已有契约；缺项记为职责缺口并交对应 agent 补全，不能从引擎默认行为推定。

**形式：异质多件套，不是单一目录。** Content 按 Phase 2 判形态；Interface 每种产物有最适形式：

| Interface 产物 | 最适形式 |
|---|---|
| 输入意图、局部状态、失败/取消与反馈时序 | 输入/反馈契约 + 具体验收场景（A）|
| 视觉外观 | 视觉稿（图像 / mockup 文件）|
| 跨屏共通规则（色 / 字 / 层级 / 动效）| 设计系统规范（单份 token 化 markdown）|
| 单屏布局 / 交互 | per-screen 蓝图 spec，引用已有输入/反馈契约 |
| 数据接线 / 引擎对象映射 / 源码位置 | 项目技术适配记录（C），由项目 / 技术适配提供 |
| code-built UI 的布局真值 | **实现即布局 SSOT**（代码文件本身，不替代行为契约）|

用一个**入口索引**（UI → 它的 spec / 规范 / 实现在哪 + 覆盖状态）把这几件串起来，而非把内容复制进一份大文档。

**content 注入接缝：运行时「是」，文档「否」。** 此处只讨论 Interface 的内容展示接缝，不把它的全部职责缩成容器：

- **运行时：通过项目适配取得内容与状态。** 可展示的 Content 定义来自 `{{data_ssot}}` 的项目投影，余额、解锁、可见性等动态状态按 Framework 契约查询；Interface 不能靠读静态内容裁决资格或扣款。
- **文档：实例真值只留指针。** Interface 文档不复制 Content 清单/数值作为第二份真值；写清字段用途与来源。验收所需的固定示例可作为明确标注的测试夹具，不能冒充当前内容清单。per-screen spec 的数据接线段引用项目技术适配记录。

**接缝引用示意（职责定义以共享引用为准）**：

```
Framework 命令/结果契约 ◀──引用── Interface 输入/反馈契约
Content 真值源          ◀──引用── Interface 展示字段
项目技术适配记录        ◀──引用── 三者的实现交接
```

**配置注意**：Interface 索引化**不需要新 config 项**——它复用已有契约 / spec / 规范 / 实现，动作是判断 + 串索引，不是 content 式提取。**不要**为它在 `split-doc-layers.config.yaml` 加 `interaction_docs` 之类的键（那会诱导走 content 式建目录，方向错）。

**Content 按形态拆出目录，Interface 优先索引已有来源；两者都保留可实施的行为契约，实例真值不重复维护。**

## 陷阱 checklist

执行完每个系统后过一遍：

- [ ] **①** 标准"凑对称"：立了三件套但有件从未被真正需要 → 先问"信息是否已在别处 + 是否会漂移"再决定保留
- [ ] **②** 手写派生数值：在内容目录里手写精确数值并标"派生自 `{{data_ssot}}`"→ 仍是漂移副本；只有 auto-dump 才是真派生（怎么做见 Phase 3「进阶：auto-dump」段）。暂不做 auto-dump 时，**跳过数值列**而非手写标"派生自..."（手写标注不免责）
- [ ] **③** 套同一模板：没有先 explore，假设所有系统都适合卡片 → 检查形态判断是否做了
- [ ] **④** spec 阶段凭理解写字段：引用了数据文件里根本不存在的字段名或实例数量 → 每个字段名 / 实例数必须从 `{{data_ssot}}` grep 确认
- [ ] **⑤** 幽灵数值：内容目录里写了数据源根本没有的字段值 → 只有"不手写数值 + 走 auto-dump"能根治
- [ ] **⑥** 契约被拆空：用共享定义的四问核对拆分前后；状态转换、失败/并发、副作用、时空单位和具体验收仍可定位，执行者无需重设计规则；技术位置与命令另标 C 层来源
