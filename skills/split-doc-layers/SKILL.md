# split-doc-layers — 设计文档三层拆分

把混写了机制算法、实例清单、精确数值的设计文档按职责拆开管理。
Content 层（里面有什么）与 Framework 和 Interface 耦合最低，最适合先拆。

**核心定位**：读项目配置 → Phase 0 判断该不该拆 → Phase 1-5 执行拆分 → 沉淀 lessons。
项目特化（数据路径、读者设定、指针位置等）全部收在 `split-doc-layers.config.yaml`，本 skill 零硬编码。

> **层覆盖**：Phase 1-5 针对 **Content 层**（拆出独立目录，最适合起步）。**Interaction 层**（怎么呈现）走**不同路径**——它常已有 SSOT（mockup / 设计系统 / spec / 实现），动作是索引化而非建目录，见 Phase 5 后专节《Interface/Interaction 层》。

---

## 启用前置：读项目配置

执行任何 Phase 前，先在项目根读 `split-doc-layers.config.yaml`。

配置 schema 见 `examples/README.md`，共 7 项：

| 配置项 | 含义 |
|---|---|
| `data_ssot` | 精确数值真值锚（如 `.tres` / `.json` 文件路径模式） |
| `framework_docs` | Framework 文档路径模式（如 `docs/GDD/*.md`） |
| `content_dir` | 内容目录位置 + 形态（如 `docs/design/*-menu.html`） |
| `semantic_field` | 数据 schema 里现成的语义字段名（逐字搬源） |
| `reader` | 内容目录目标读者（`designer` / `player` / 自定义） |
| `pointer_loc` | 双向指针两端位置描述（格式 `内容目录端 ↔ Framework端`） |
| `forbid_pattern` | 防回退精确数值正则（标注用，如 `[0-9]+\.[0-9]+`） |

配置文件不存在时，先引导用户参考 `examples/README.md` 建一份，再继续。

## Phase 0 — Guard：该不该拆？

**满足任一跳过条件即跳过拆分（避免形式大于内容）：**

- [ ] DriftPredictor = 文档改频 ÷ 相关代码/数据改频 < 0.2 → 文档已被代码替代，不需拆
  **无 git 历史 / 无法计算时**：用 `{{framework_docs}}` 版本号或修订频率 vs 数据文件字段稳定性做定性比较；或直接跳过此条，用下方"可继续的信号"判断——DriftPredictor 是辅助信号，不是硬门槛。
- [ ] 目标系统的 Content 层不厚（实例 < 3 个，且无独立描述价值）→ 机制驱动型，保留在 Framework 文档即可
- [ ] 数值本身即 content 主体（纯数值对比表/参数手册）→ 本方法论不适用，见 frontmatter"不适用"

**可继续的信号（满足以下任一即继续）：**

- 文档里有完整实例清单 + 机制算法混写
- 每次调参需要同步文档（漂移已经发生）
- 实例数量 ≥ 3 且实例有独立的描述价值

## Phase 1 — 定读者

从 `{{reader}}` 配置读目标读者，确认内容目录的边界：

| 读者 | 可放 | 不可放 |
|---|---|---|
| **玩家（config reader: player）** | 身份摘要（一句话）、文案、视觉标识 | 实施细节（signal/算法）；设计推荐；精确数值 |
| **设计师/开发者（config reader: designer）** | 身份摘要 + 实施细节；identity 属性（弱点/标签等）；功能组合推荐 | 精确数值（留 `{{data_ssot}}`）|
| **自定义（config reader: 其他值）** | 参照 designer 规则作默认基准，按描述调整 | — |

同一项目不同内容目录可能目标读者不同——先确认再画边界。

---

## Phase 2 — 判形态

**先 explore、别套模板**。对每个目标系统独立判断 content 形态：

| 形态 | 适用场景 | 建议文档形式 |
|---|---|---|
| **并列实例型** | 实例多、数量并列（角色图鉴/配料清单/天气清单） | 独立内容目录：卡片式（HTML 图鉴、卡片表） |
| **映射型** | 输入→输出映射（配方表、升级对照） | 表格 |
| **序列型** | 有时序关系（关卡编排/日程表） | 时间线 / 按序号列表 |
| **层级/树型** | 有父子关系（升级树/技能树） | 嵌套结构 / 树图 |
| **机制驱动聚合型** | Content 只是算法参数的聚合，实例本身很薄 | **不强拆**——留在 Framework 文档 |

**关键判断**：content 驱动型（实例多/并列/有独立描述价值）→ 拆独立内容目录；机制驱动型 → 不强做图鉴。

推广多个系统时，逐个 explore，不假设"上一个是卡片所以这个也是卡片"。

**首次拆分 / 要推广到多个系统时：先选一个最典型系统（实例多、最适合卡片）试点，走完 Phase 2-5 + 陷阱 checklist，回审"哪条标准从未被真正用到"，等用户确认后再推广其余系统——逐个 explore，不批量套同一模板。**

## Phase 3 — 提取 Content

**提取前先确定「实例单位」**：明确这个系统的实例是什么维度——个体 / 类别 / 属性档 / 矩阵格子。多维系统尤其要先定（如「物种 × 稀有度」既可按物种、也可按稀有度档、还可按矩阵格子组织内容目录，三种选法结论完全不同）。判断来源：从 `{{framework_docs}}` 的 §2 核心循环 / §3 机制清单找该系统的实例维度；无明确实例清单时，以 §1.2 设计意图的**主线维度**为实例。不同实例单位 → 不同内容目录结构，定错会整份返工。

**进内容目录：**
- 实例清单（该系统所有实例）
- 身份摘要：读者视角"这个实例在做什么"——一句话，不给精确数值；实施细节和克制关系按 `{{reader}}` 决定
- 文案（玩家可见的名称/标签/提示文字）
- 视觉标识（图标 id / 颜色分类）
- 关系标签（定性词，非精确数）

**不进内容目录：**
- **精确数值**：hp / 速度 / 倍率等精确数字 → 留 `{{data_ssot}}`（防 stale 漂移）；想给读者量级感用定性档位（"中等血量/速度偏慢"），不写精确数字
- **FIXME 占位值**：尚未校准的值漂移风险更高，尤其不进内容目录
- 实施细节（玩家读者）：状态机逻辑/公式/信号名 → 留 Framework 文档
- 临时设计推荐：即兴的克制建议/搭配推荐 → 不写（易 stale）；但数据 schema 已有的 identity 属性可进
- 视觉规格：进度环/飘字动效/颜色 hex 规格 → 留 Interface 层

**身份摘要最高效来源**：先 grep `{{data_ssot}}` schema，找有没有 `{{semantic_field}}` 等现成语义字段。有就**逐字搬**，不提炼不改写——"逐字搬现成字段"是零漂移。

逐字搬前提：仅当该字段是面向目标读者的自然语言描述；若是工程师内部技术描述（如 `CHASE_IF_DIST_LT_200`）→ 仍需提炼，并显式标为漂移高风险点，定期核对。

**`{{semantic_field}}` 配置为 `none`（无现成语义字段）时的提炼路径：**

1. **从哪提炼**：从 `{{framework_docs}}` 的设计意图段（如 §1.2 体验设计 / §3.1 核心机制描述）提炼，这是最接近"对读者有意义的描述"的来源。
2. **提炼模板**：`[实例名]：[一句话核心身份]（来源：{{framework_docs}} §X.Y）`
   - 示例：`小鸡：孵化速度最快的入门动物，适合新手学习节奏（来源：docs/design/gdd/animal.md §1.2）`
3. **提炼粒度**：多段设计意图压缩为一句身份摘要——不整段搬，提炼"这个实例在玩家/设计师眼中是什么"。
4. **精确数值不进摘要**：用定性档位替代（"孵化最快"而非"孵化需 1 秒"；"稀有度高"而非"稀有度概率 5%"）。
5. **漂移风险标注**：每条提炼摘要旁加注释，格式：
   ```
   <!-- 高漂移：本句从 {{framework_docs}} §X.Y 手动提炼，源文档更新后需同步核对 -->
   ```

**tag 配色规范**：同一语义维度的标签必须同色，只有不同维度才换色。在样式系统里统一定义，不在每张卡片里各自内联。

### 进阶：auto-dump —— 让内容目录从 `{{data_ssot}}` 自动生成

前面多处强调"手写数值会漂、只有 auto-dump 是真派生"——这里给落地方法。auto-dump = 写脚本从 `{{data_ssot}}` 自动生成内容目录，改数据一处、重跑即同步。**它解锁了手动提取做不到的事：数值可以安全进内容目录**（自动同步不再漂移）——这是相对手动提取的关键升级。但「要不要 dump 数值」仍看 `{{reader}}` 与设计意图：防查表化的玩家图鉴即使能 auto-dump 也可只放语义；设计师内部目录可放全数值。

**何时值得建**（满足多条再做，否则手动提取够用）：
- 内容目录的数值/字段频繁随调参漂、手动同步成本高
- 实例多到手维护不值（经验阈值 > 20）
- `{{data_ssot}}` 是机器可读格式（文本，或可导出文本）

**引擎无关的 4 步 pipeline：**

```
1 读 {{data_ssot}} → 2 解析成「实例列表」(统一中间表示) → 3 套模板渲染 → 4 写 {{content_dir}}
```

只有第 1 步「读」与引擎/数据格式相关，第 2-4 步完全通用。

**第 1 步「读」按 `{{data_ssot}}` 格式实现（引擎差异挡在这一步）：**

| 格式 | 怎么读到「实例列表」 |
|---|---|
| CSV / JSON / YAML | 标准库直接解析，无引擎依赖 |
| Godot `.tres` | 本身是文本，正则/解析提字段；或 GDScript 导出 |
| Unreal DataTable | 编辑器 **Export to CSV**（或 Unreal Python API）→ 走 CSV 路径 |
| 任何引擎兜底 | 都能 Export CSV / JSON → 之后下游完全统一 |

**关键**：任何引擎都能把数据导出成 CSV/JSON 文本中介，导出后第 2-4 步殊途同归——引擎差异不进 pipeline 主体。

**第 3 步「渲染」按 `{{content_dir}}` 形态**（HTML 图鉴 / Markdown 表…）——内容形态相关、非引擎相关。渲染时仍守上方 Phase 3 边界（实施细节 / 视觉规格不进）。

**别从零造**：auto-dump 是「数据源 → 生成物」生成器，与本插件 `generate-assets` skill 同构（一个生文档目录、一个生图片）。参考其 `data_source.py` 的数据源加载思路（json_dict / json_list / inline + filter），不重造轮子。

**落地原则**：具体脚本按上面骨架在**项目侧**实现（语言 / 引擎随项目，不进通用 skill）；建成后在内容目录 footer 标注「本目录由 `<脚本>` 从 `{{data_ssot}}` 自动生成，勿手改」。

## Phase 4 — 双向指针

按 `{{pointer_loc}}` 配置，在两端各加一件指针，构成导航闭环即够——不要第三件（第三件=手写中央索引，含代码路径、随文件重构漂移）。

1. **内容目录 → Framework**：footer 或头部说明，链接 Framework 文档 + `{{data_ssot}}`（精确数值在哪）
2. **Framework → 内容目录**：在"速查/快速参考"段加一行"内容目录 → `xxx-menu.html`"（或对应路径）

手写维护的静态中央索引（把所有系统的框架/内容位置集中列在一处）会随文件重构漂移——需要全局总览时，用 Glob/CI 脚本自动生成，不手写。自动生成的总览索引是**永久产物**（手写版的升级形态），推广完成后不删除。

## Phase 5 — Framework 瘦身

拆出 content 目录后，对 `{{framework_docs}}` 做最小改动：

**保留**（不删）：
- 设计意图叙事中的 content 举例（举例是机制说明必需的，不能删）
- 设计禁区 / 体验目标（高层定性描述）
- 机制算法 / 公式

**指针化**（只加，不删叙事）：
- 完整实例清单段 → 加一行指针到内容目录，完整清单本体**不再独立维护**；若保留须注明"以内容目录为准，本段不再独立维护"
- 全数值表 → 加指针到 `{{data_ssot}}`

实践中若 Framework 文档本就不含完整清单，"瘦身"主要就是加指针，改动极轻。

## Interface/Interaction 层：与 Content 不对称，多是「索引化」非「建目录」

> 上面 Phase 1-5 是 **Content 层**的拆分管线。Interaction 层（怎么呈现）**不走同一套**——照搬会造双 SOT。

**关键不对称**：Content 值得拆出独立目录，前提是**拆前无独立家**（语义字段散在 `{{data_ssot}}`、无人类可读投影）。Interaction 层往往**相反**——它早有自己的 SSOT 群，只是不在 `{{framework_docs}}` 里：

- 视觉稿（mockup / 设计图）
- 设计系统规范（色 / 字 / 层级 / 动效 token，单份）
- 单屏蓝图（per-screen spec）
- **实现本身**（代码建的 UI，其布局即 SSOT）

→ **Interaction 的"拆分"多半是"用一个索引把已有的家串起来 + 确认 `{{framework_docs}}` 只留意图（WHY）"，不是新建一份目录。** 给已有家的内容再建 catalog = 第 N+1 个 SSOT = 双 SOT。复用 Phase 0 判据：对每个候选 interaction 产物问"拆前有没有独立家"——有家则只索引、不新建；确实无家且同质并列（罕见）才考虑 content 式目录。

> ⚠️ 实战教训：覆盖审计常把"没有 spec 文件的 UI"误报为"待补盲区"，但它的设计意图可能记在别处（决策档 / 实施 plan / 代码头注释），布局真值就在实现里。**写新 spec 前必先核实它是否已有家**——否则写出的就是违规重复 SOT。

**形式：异质多件套，不是单一目录。** Content 同质（实例 → 单一卡片目录）；Interaction 异质，每种内容有最适形式：

| interaction 内容 | 最适形式 |
|---|---|
| 视觉外观 | 视觉稿（图像 / mockup 文件）|
| 跨屏共通规则（色 / 字 / 层级 / 动效）| 设计系统规范（单份 token 化 markdown）|
| 单屏布局 / 交互 / 数据接线 | per-screen 蓝图 spec |
| code-built UI 的布局真值 | **实现即 SSOT**（代码文件本身）|

用一个**入口索引**（UI → 它的 spec / 规范 / 实现在哪 + 覆盖状态）把这几件串起来，而非把内容复制进一份大文档。

**content 注入接缝：运行时「是」，文档「否」。** Interaction 是容器 / 结构，Content 是填充，两层在"注入"接缝相遇——方向相反：

- **运行时：应注入，三层正交的健康标志。** UI 容器运行时读 `{{data_ssot}}` 填自己（容器只定义"结构 + 交互行为"，填什么由 Content 层运行时给）。
- **文档：禁止硬拷贝，只能指针。** Interaction 文档**不得**把 content 值抄进去（spec 里不列实例名 / 数值）——抄即双 SOT（值的 SSOT 在 `{{data_ssot}}`，抄进必漂）。正确是**接线指针**（"网格按 `{{data_ssot}}` 实例序填"）。per-screen spec 的"数据接线 / Logic→View"段记的就是这个接缝。

**三层接缝心智模型**：

```
Framework   = 怎么运转（机制意图；UI 反馈的 WHY 留 {{framework_docs}}）
Content     = 里面有什么（数据实例 → 内容目录）
Interaction = 容器 / 呈现（视觉稿 + token 规范 + 单屏蓝图 + 实现）

运行时：content ──注入──▶ interaction 容器   （代码读 {{data_ssot}} 填 UI）
文档  ：三层互相只──指针──不复制              （spec 写"由 X 填"，不写实例值）
```

**配置注意**：interaction 索引化**不需要新 config 项**——它复用已有 spec / 规范 / 实现，动作是判断 + 串索引，不是 content 式提取。**不要**为它在 `split-doc-layers.config.yaml` 加 `interaction_docs` 之类的键（那会诱导走 content 式建目录，方向错）。

一句话：**Content 拆"出来"（建目录），Interaction 多半拆"清楚"（索引已有的家）；content 注入是运行时的事，文档层只留指针——嵌 content 即破"不双 SOT"红线。**

## 陷阱 checklist

执行完每个系统后过一遍：

- [ ] **①** 标准"凑对称"：立了三件套但有件从未被真正需要 → 先问"信息是否已在别处 + 是否会漂移"再决定保留
- [ ] **②** 手写派生数值：在内容目录里手写精确数值并标"派生自 `{{data_ssot}}`"→ 仍是漂移副本；只有 auto-dump 才是真派生（怎么做见 Phase 3「进阶：auto-dump」段）。暂不做 auto-dump 时，**跳过数值列**而非手写标"派生自..."（手写标注不免责）
- [ ] **③** 套同一模板：没有先 explore，假设所有系统都适合卡片 → 检查形态判断是否做了
- [ ] **④** spec 阶段凭理解写字段：引用了数据文件里根本不存在的字段名或实例数量 → 每个字段名 / 实例数必须从 `{{data_ssot}}` grep 确认
- [ ] **⑤** 幽灵数值：内容目录里写了数据源根本没有的字段值 → 只有"不手写数值 + 走 auto-dump"能根治

## 执行流程总图

```
读项目配置（split-doc-layers.config.yaml）
    ↓
Phase 0 Guard（跳过 or 继续）
    ↓
Phase 1 定读者（{{reader}}）
    ↓
Phase 2 判形态（每个目标系统独立 explore）
```
